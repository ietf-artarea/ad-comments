12	Abstract

14	   This document defines protocol mapping extensions for the Semantic
15	   Definition Format (SDF) to enable mapping of protocol-agnostic SDF
16	   affordances to protocol-specific operations.  The protocol mapping
17	   mechanism allows SDF models to specify how properties, actions, and
18	   events should be accessed using a specific protocol.  This document
19	   defines protocol mappings for Bluetooth Low Energy and Zigbee, and
20	   the mechanism can be extended to other protocols such as HTTP and
21	   CoAP.  This document also describes a method to extend SCIM with an
22	   SDF model mapping.

109	1.  Introduction

111	   The Semantic Definition Format (SDF) [RFC9880] provides a protocol-
112	   agnostic way to describe IoT devices and their capabilities through
113	   properties, actions, and events (collectively called affordances).  A
114	   device described by an SDF model, however, is accessed over a
115	   specific communication protocol.  To interact with such a device
116	   based on its SDF model, there needs to be a mechanism to map the
117	   protocol-agnostic SDF definitions to the protocol-specific operations
118	   that access the device.  Moreover, such a mechanism needs to be
119	   extensible for enabling implementers to provide novel SDF protocol
120	   mappings to expand the SDF ecosystem.  SDF protocol mappings may
121	   target a variety of protocols spanning from non-IP protocols commonly
122	   used in IoT environments, such as [BLE53] and [Zigbee30], to IP-based
123	   protocols such as HTTP [RFC9110] and CoAP [RFC7252].  This document
124	   provides the required mechanism by defining:

126	   *  The sdfProtocolMap quality, which allows SDF models to include
127	      protocol-specific mapping information attached to the protocol-
128	      agnostic definitions, see Section 3.  An sdfProtocolMap MAY be
129	      applied to an SDF affordance, be it an sdfProperty, sdfEvent or
130	      sdfAction.  The mapping enables use cases such as application
131	      gateways or multi-protocol gateways that translate between
132	      different IoT protocols, automated generation of protocol-specific
133	      implementations from SDF models, and interoperability across
134	      heterogeneous device ecosystems.

136	   *  Two SDF protocol mappings for Bluetooth and Zigbee protocols, see
137	      Section 4.1 and Section 4.2 respectively.

139	   *  An SDF model extension for SCIM.  While SDF provides a way to
140	      describe a class of devices, SCIM describes a device instance.
141	      The SDF model extension for SCIM enables the inclusion of SDF
142	      models for the class of devices a device belongs to in the SCIM
143	      object, see Section 5.

145	   *  An IANA registry for defining additional SDF protocol mappings (in
146	      addition to the BLE and Zigbee provided in this document), see
147	      Section 8.1.

161	3.  SDF Protocol Mapping Structure

163	   This section defines the structure of an sdfProtocolMap.  Because
164	   each protocol has its own addressing model, a single SDF affordance
165	   requires a distinct mapping per protocol.  For example, BLE addresses
166	   a property as a service characteristic, while Zigbee addresses it as
167	   an attribute in a cluster of an endpoint.

169	   The value of the sdfProtocolMap quality is a JSON object nested
170	   inside an SDF affordance definition (sdfProperty, sdfAction, or
171	   sdfEvent).  Protocol-specific attributes are embedded within this
172	   object, keyed by a protocol name registered in the IANA "SDF Protocol
173	   Mapping" registry (Section 8.1), e.g., "ble" or "zigbee".

175	   sdfProperty / sdfAction / sdfEvent
176	     |
177	     +-----> sdfProtocolMap
178	               |
179	               +-----> ble
180	               |        |
181	               |        +--> BLE-specific mapping
182	               |
183	               +-----> zigbee
184	               |        |
185	               |        +--> Zigbee-specific mapping
186	               |
187	               +-----> ...

189	                  Figure 1: SDF Protocol Mapping Structure

191	3.1.  SDF Extension Points

193	   The sdfProtocolMap quality is introduced into SDF affordance
194	   definitions through the extension points defined in the formal syntax
195	   of Appendix A of [RFC9880].  For each affordance type, an
196	   sdfProtocolMap entry is added via the corresponding CDDL group
197	   socket.  The contents of the sdfProtocolMap object are in turn
198	   extensible through a protocol-mapping-specific group socket.

200	   A protocol MAY choose to extend only the affordance types that are
201	   applicable to it.  For example, the BLE protocol mapping defines
202	   extensions for properties and events but not for actions.

204	3.1.1.  Property Extension

206	   The $$SDF-EXTENSION-PROPERTY group socket in the propertyqualities
207	   rule of Appendix A of [RFC9880] is used to add protocol mapping to
208	   sdfProperty definitions:

210	   $$SDF-EXTENSION-PROPERTY //= (
211	     sdfProtocolMap: {
212	       * $$SDF-PROPERTY-PROTOCOL-MAP
213	     }
214	   )

216	   property-protocol-map<name, props, read-props, write-props> = (
217	     name => props /
218	       {
219	         read: read-props,
220	         write: write-props
221	       }
222	   )
223	        Figure 2: SDF Property Extension Point for Protocol Mapping

225	   The property-protocol-map generic (Figure 2) captures the common
226	   structure of property protocol mappings.  The name parameter is the
227	   protocol name and props is the protocol-specific map of attributes.
228	   A protocol can provide either:

230	   *  A single mapping that applies to both read and write operations,
231	      or

233	   *  Separate read and write mappings when the protocol uses different
234	      attributes for each direction.

236	   To keep these two forms unambiguous, the protocol-specific attribute
237	   map (the props type) MUST NOT define members named read or write.

239	   To extend $$SDF-PROPERTY-PROTOCOL-MAP for a new protocol (e.g., "new-
240	   protocol"), implementers MUST use the property-protocol-map generic
241	   with the protocol name and a map type defining the protocol-specific
242	   attributes.

244	   It is to be noted that the protocol name (e.g., "new-protocol") MUST
245	   be registered in the IANA registry defined in Section 8.1.

247	   For a fictitious "new-protocol" that uses the same attributes for
248	   both read and write operations, the generic invocation could be
249	   defined as:

251	   =============== NOTE: '\' line wrapping per RFC 8792 ================

253	   $$SDF-PROPERTY-PROTOCOL-MAP //= (
254	     property-protocol-map<"new-protocol", new-protocol-property, new-\
255	                               protocol-property, new-protocol-property>
256	   )

258	   new-protocol-property = {
259	     attributeA: text,
260	     attributeB: uint
261	   }

263	             Figure 3: Example Property Protocol Map Extension

265	   An SDF model using a single mapping for both read and write
266	   operations could look like:

268	   {
269	     "sdfProperty": {
270	       "temperature": {
271	         "type": "number",
272	         "unit": "Cel",
273	         "sdfProtocolMap": {
274	           "new-protocol": {
275	             "attributeA": "temperature-service",
276	             "attributeB": 1
277	           }
278	         }
279	       }
280	     }
281	   }

283	       Figure 4: Example Property Protocol Map with a Single Mapping

285	   An SDF model using separate read and write mappings could look like:

287	   {
288	     "sdfProperty": {
289	       "temperature": {
290	         "type": "number",
291	         "unit": "Cel",
292	         "sdfProtocolMap": {
293	           "new-protocol": {
294	             "read": {
295	               "attributeA": "temperature-read-service",
296	               "attributeB": 1
297	             },
298	             "write": {
299	               "attributeA": "temperature-write-service",
300	               "attributeB": 2
301	             }
302	           }
303	         }
304	       }
305	     }
306	   }

308	       Figure 5: Example Property Protocol Map with Separate Read and
309	                               Write Mappings

311	   When a protocol instead uses different attributes for read and write
312	   operations, the read-props and write-props type parameters can be
313	   given distinct types:

315	   =============== NOTE: '\' line wrapping per RFC 8792 ================

317	   $$SDF-PROPERTY-PROTOCOL-MAP //= (
318	     property-protocol-map<"new-protocol", new-protocol-property, new-\
319	                    protocol-property-read, new-protocol-property-write>
320	   )

322	   new-protocol-property-read = {
323	     attributeA: text
324	   }

326	   new-protocol-property-write = {
327	     attributeA: text,
328	     attributeB: uint
329	   }

331	      Figure 6: Example Property Protocol Map Extension with Distinct
332	                       Read and Write Attribute Types

334	   An SDF model using this extension could look like:

336	   {
337	     "sdfProperty": {
338	       "temperature": {
339	         "type": "number",
340	         "unit": "Cel",
341	         "sdfProtocolMap": {
342	           "new-protocol": {
343	             "read": {
344	               "attributeA": "temperature-read-service"
345	             },
346	             "write": {
347	               "attributeA": "temperature-write-service",
348	               "attributeB": 2
349	             }
350	           }
351	         }
352	       }
353	     }
354	   }

359	3.1.2.  Action Extension

361	   The $$SDF-EXTENSION-ACTION group socket in the actionqualities rule
362	   of Appendix A of [RFC9880] is used to add protocol mapping to
363	   sdfAction definitions:

365	   $$SDF-EXTENSION-ACTION //= (
366	     sdfProtocolMap: {
367	       * $$SDF-ACTION-PROTOCOL-MAP
368	     }
369	   )

371	         Figure 8: SDF Action Extension Point for Protocol Mapping

373	   Actions use a simpler structure than properties, as they do not
374	   require the read/write distinction.  To extend $$SDF-ACTION-PROTOCOL-
375	   MAP for a new protocol, implementers MUST add a group entry that maps
376	   the protocol name to the protocol-specific attributes.  For example,
377	   an extension for a fictitious "new-protocol" could be defined as:

379	   $$SDF-ACTION-PROTOCOL-MAP //= (
380	     "new-protocol": new-protocol-action
381	   )

383	   new-protocol-action = {
384	     commandID: uint
385	   }

387	              Figure 9: Example Action Protocol Map Extension

389	   An SDF model using this extension could look like:

391	   {
392	     "sdfAction": {
393	       "reset": {
394	         "sdfProtocolMap": {
395	           "new-protocol": {
396	             "commandID": 42
397	           }
398	         }
399	       }
400	     }
401	   }

403	               Figure 10: Example Action Protocol Map in JSON

451	3.2.  Reusing Protocol Mappings

453	   Affordances often share most of their protocol mapping, e.g. when
454	   several Zigbee attributes are reached through the same endpoint and
455	   application profile.  The sdfRef quality (Section 4.4 of [RFC9880])
456	   can then be used to base one affordance definition on another and
457	   patch only the differing protocol attributes; a null value removes an
458	   inherited one.  A definition (e.g., sdfProperty) intended only for
459	   such reuse can be placed at the top level of the SDF model
460	   (Section 3.4 of [RFC9880]), where it does not declare an affordance
461	   of any sdfObject.

463	   For example, with two Zigbee attributes on the same endpoint and
464	   profile:

466	   {
467	     "sdfProperty": {
468	       "zigbeeTemperatureAttributeBase": {
469	         "type": "number",
470	         "unit": "Cel",
471	         "sdfProtocolMap": {
472	           "zigbee": {
473	             "endpointID": 1,
474	             "profileID": 260,
475	             "clusterID": 1026,
476	             "attributeID": 0,
477	             "attributeType": 41
478	           }
479	         }
480	       }
481	     },
482	     "sdfObject": {
483	       "sensor": {
484	         "sdfProperty": {
485	           "temperature": {
486	             "sdfRef": "#/sdfProperty/zigbeeTemperatureAttributeBase"
487	           },
488	           "humidity": {
489	             "sdfRef": "#/sdfProperty/zigbeeTemperatureAttributeBase",
490	             "unit": "%RH",
491	             "minimum": 0,
492	             "sdfProtocolMap": {
493	               "zigbee": {
494	                 "clusterID": 1029,
495	                 "attributeType": 33
496	               }
497	             }
498	           }
499	         }
500	       }
501	     }
502	   }

504	              Figure 14: Reusing a Protocol Mapping via sdfRef

506	   humidity adds a minimum of its own and restates only the two Zigbee
507	   attributes that differ, clusterID and attributeType; endpointID,
508	   profileID, and attributeID come from the base.  Adding "profileID":
509	   null there would drop the profile instead of inheriting it.

511	   The CDDL here describes resolved models (Section 4.4.1 of [RFC9880])
512	   and does not admit sdfRef inside the protocol-specific attribute
513	   maps.  A definition supplying only the differing attributes therefore
514	   conforms to this specification only once sdfRef has been resolved.
515	   The referenced definition remains part of the resolved model, so it
516	   has to carry a complete and valid protocol mapping.

518	4.  Registered Protocol Mappings

520	   This section defines the protocol mappings registered by this
521	   document.

523	4.1.  BLE

525	   The BLE protocol mapping allows SDF models to specify how properties
526	   and events should be accessed using Bluetooth Low Energy (BLE)
527	   protocol [BLE53].  The mapping includes details such as service IDs
528	   and characteristic IDs that are used to access the corresponding SDF
529	   affordances.

531	4.1.1.  Properties

533	   For sdfProperty, the BLE protocol mapping structure is defined as
534	   follows:

536	   =============== NOTE: '\' line wrapping per RFC 8792 ================

538	   $$SDF-PROPERTY-PROTOCOL-MAP //= (
539	     property-protocol-map<"ble", ble-property, ble-property, ble-\
540	                                                               property>
541	   )

543	   ble-property = {
544	     serviceID: text,
545	     characteristicID: text
546	   }

548	    Figure 15: CDDL definition for BLE Protocol Mapping for sdfProperty

550	   Where:

552	   *  serviceID is the BLE service ID that corresponds to the SDF
553	      property.

555	   *  characteristicID is the BLE characteristic ID that corresponds to
556	      the SDF property.

558	   For example, a BLE protocol mapping for a temperature property:

560	   {
561	     "sdfProperty": {
562	       "temperature": {
563	         "sdfProtocolMap": {
564	           "ble": {
565	             "serviceID": "00001809-0000-1000-8000-00805f9b34fb",
566	             "characteristicID": "00002a1c-0000-1000-8000-00805f9b34fb"
567	           }
568	         }
569	       }
570	     }
571	   }

573	   For a temperature property that has different mappings for read and
574	   write operations, here is an example of the BLE protocol mapping:

576	   =============== NOTE: '\' line wrapping per RFC 8792 ================

578	   {
579	     "sdfProperty": {
580	       "temperature": {
581	         "sdfProtocolMap": {
582	           "ble": {
583	             "read": {
584	               "serviceID": "00001809-0000-1000-8000-00805f9b34fb",
585	               "characteristicID": "00002a1c-0000-1000-8000-\
586	                                                           00805f9b34fb"
587	             },
588	             "write": {
589	               "serviceID": "00001809-0000-1000-8000-00805f9b34fb",
590	               "characteristicID": "00002a51-0000-1000-8000-\
591	                                                           00805f9b34fb"
592	             }
593	           }
594	         }
595	       }
596	     }
597	   }

599	4.1.2.  Events

601	   For sdfEvents, the BLE protocol mapping structure is similar to
602	   sdfProperties, but it MUST additionally include at least the type of
603	   the event.

605	   $$SDF-EVENT-PROTOCOL-MAP //= (
606	     ble: ble-event-map
607	   )

609	   ble-event-map = {
610	     type: "gatt",
611	     serviceID: text,
612	     characteristicID: text
613	   } / { type: "advertisements" } / { type: "connection_events" }

615	               Figure 16: BLE Protocol Mapping for sdfEvents

617	   Where:

619	   *  type specifies the type of BLE event, such as "gatt" for GATT
620	      events, "advertisements" for advertisement events, or
621	      "connection_events" for connection-related events.

623	   *  serviceID and characteristicID identify the GATT service and
624	      characteristic.  They MUST be present when type is "gatt", and
625	      MUST be absent when type is "advertisements" or
626	      "connection_events".

628	   For example, a BLE event mapping for a heart rate measurement event:

630	   {
631	     "sdfEvent": {
632	       "heartRate": {

637	             "characteristicID": "00002a37-0000-1000-8000-00805f9b34fb"
638	           }
639	         }
640	       }
641	     }
642	   }

646	   {
647	     "sdfEvent": {

658	4.2.  Zigbee

660	   The Zigbee protocol mapping allows SDF models to specify how
661	   properties, actions, and events should be accessed using the Zigbee
662	   protocol [Zigbee30].  The mapping includes details such as cluster
663	   IDs and attribute IDs that are used to access the corresponding SDF
664	   affordances.

666	4.2.1.  Properties

668	   An sdfProperty is mapped to a Zigbee cluster attribute.  The Zigbee
669	   property protocol mapping structure is defined as follows:

671	   =============== NOTE: '\' line wrapping per RFC 8792 ================

673	   $$SDF-PROPERTY-PROTOCOL-MAP //= (
674	     property-protocol-map<"zigbee", zigbee-property, zigbee-property, \
675	                                                        zigbee-property>
676	   )

678	   zigbee-property = {
679	     endpointID: uint,
680	     clusterID: uint,
681	     attributeID: uint,
682	     attributeType: uint,
683	     ? profileID: uint,
684	     ? manufacturerCode: uint,
685	   }

687	         Figure 17: CDDL definition for Zigbee Protocol Mapping for
688	                                sdfProperty

690	   Where:

692	   *  endpointID is the Zigbee endpoint ID that corresponds to the SDF
693	      property.

695	   *  clusterID is the Zigbee cluster ID that corresponds to the SDF
696	      property.

698	   *  attributeID is the Zigbee attribute ID that corresponds to the SDF
699	      property.

701	   *  attributeType is the Zigbee data type of the attribute, as defined
702	      by the Zigbee Cluster Library [ZCL7].

704	   *  profileID is the Zigbee application profile ID (optional).  If not
705	      provided, it defaults to the Home Automation profile (0x0104),
706	      which is the default application profile defined in [Zigbee30].

708	   *  manufacturerCode is the Zigbee manufacturer code of the attribute
709	      (optional).

711	   For example, a Zigbee protocol mapping for a temperature property may
712	   look as follows:

714	   {
715	     "sdfProperty": {
716	       "temperature": {
717	         "sdfProtocolMap": {
718	           "zigbee": {
719	             "endpointID": 1,
720	             "clusterID": 1026,
721	             "attributeID": 0,
722	             "attributeType": 41,
723	             "profileID": 260
724	           }
725	         }
726	       }
727	     }
728	   }

730	4.2.2.  Events

732	   An sdfEvent is mapped to a Zigbee cluster event such as attribute
733	   reporting, a device-initiated write to an attribute on the gateway,
734	   or a cluster command.  The Zigbee event protocol mapping structure is
735	   defined as follows.  The "attribute_reporting" and "write_event"
736	   variants reuse the zigbee-property definition from Figure 17 to
737	   identify the underlying Zigbee attribute:

739	   =============== NOTE: '\' line wrapping per RFC 8792 ================

741	   $$SDF-EVENT-PROTOCOL-MAP //= (
742	     zigbee: zigbee-event-map
743	   )

745	   zigbee-event-map = zigbee-attribute-reporting / zigbee-write-event \
746	                / zigbee-connection-event / zigbee-cluster-command-event

748	   zigbee-attribute-reporting = {
749	     type: "attribute_reporting",
750	     ~zigbee-property,
751	     ? minReportingInterval: uint,
752	     ? maxReportingInterval: uint,
753	     ? reportableChange: number,
754	   }

756	   zigbee-write-event = {
757	     type: "write_event",
758	     ~zigbee-property,
759	   }

761	   zigbee-connection-event = {
762	     type: "connection_events",
763	   }

765	   zigbee-cluster-command-event = {
766	     type: "cluster_command",
767	     endpointID: uint,
768	     clusterID: uint,
769	     commandID: uint,
770	     direction: "client_to_server" / "server_to_client",
771	     ? profileID: uint,
772	     ? manufacturerCode: uint,
773	   }

775	    Figure 18: CDDL definition for Zigbee Protocol Mapping for sdfEvents

777	   Where:

779	   *  type is the type of Zigbee event.  It MUST be one of:

781	      -  "attribute_reporting": the event is triggered by Zigbee
782	         attribute reporting.

784	      -  "write_event": the event is triggered by the device writing to
785	         an attribute on the gateway.

787	      -  "connection_events": the event is triggered when a Zigbee end
788	         device joins or leaves the Zigbee network.

790	      -  "cluster_command": the event is triggered by a ZCL cluster-
791	         specific command.

793	   *  endpointID, clusterID, attributeID, attributeType, profileID, and
794	      manufacturerCode have the same meaning as described for
795	      sdfProperty in Figure 17.  These fields are present when type is
796	      "attribute_reporting" or "write_event", and MUST be absent when
797	      type is "connection_events".

799	   *  For "cluster_command", endpointID identifies the originating
800	      Zigbee end device's source endpoint, clusterID identifies the
801	      cluster, and commandID identifies the cluster-specific command.
802	      direction identifies the ZCL command direction and MUST be
803	      present.  It cannot be inferred from the coordinator role: the
804	      gateway can be either the ZCL client or the ZCL server. profileID
805	      and manufacturerCode have the same meaning as in Figure 17.

807	   *  minReportingInterval is the minimum reporting interval in seconds
808	      (optional).  It is the minimum time between issued attribute
809	      reports and only applies when type is "attribute_reporting".

811	   *  maxReportingInterval is the maximum reporting interval in seconds
812	      (optional).  It is the maximum time between issued attribute
813	      reports and only applies when type is "attribute_reporting".

815	   *  reportableChange is the minimum change to the attribute value that
816	      triggers a report (optional).  It only applies when type is
817	      "attribute_reporting" and to attributes whose attributeType is one
818	      of the "analog" data types defined by the Zigbee Cluster Library
819	      [ZCL7] (e.g., unsigned and signed integers, floating point
820	      numbers), as opposed to "discrete" data types (e.g., booleans,
821	      enumerations, bitmaps), for which reporting a minimum change is
822	      not meaningful.  The value is interpreted in the same Zigbee data
823	      type as the reported attribute's attributeType.

825	   For example, a Zigbee event mapping for a temperature change report:

827	   {
828	     "sdfEvent": {
829	       "temperatureChange": {
830	         "sdfProtocolMap": {
831	           "zigbee": {
832	             "type": "attribute_reporting",
833	             "profileID": 260,
834	             "endpointID": 1,
835	             "clusterID": 1026,
836	             "attributeID": 0,
837	             "attributeType": 41,
838	             "minReportingInterval": 10,
839	             "maxReportingInterval": 300,
840	             "reportableChange": 50
841	           }
842	         }
843	       }
844	     }
845	   }

847	   For example, a Zigbee switch sends an On command from its On/Off
848	   cluster client to the gateway's On/Off cluster server:

850	   {
851	     "sdfEvent": {
852	       "on": {
853	         "sdfProtocolMap": {
854	           "zigbee": {
855	             "type": "cluster_command",
856	             "profileID": 260,
857	             "endpointID": 1,
858	             "clusterID": 6,
859	             "commandID": 1,
860	             "direction": "client_to_server"
861	           }
862	         }
863	       }
864	     }
865	   }

867	   Here is an example of an isPresent event using Zigbee connection
868	   events:

870	   {
871	     "sdfEvent": {
872	       "isPresent": {
873	         "sdfProtocolMap": {
874	           "zigbee": {
875	             "type": "connection_events"
876	           }
877	         }
878	       }
879	     }
880	   }

882	4.2.3.  Actions

884	   An sdfAction is mapped to a Zigbee cluster command.  The Zigbee
885	   protocol mapping structure for actions is defined as follows:

887	   $$SDF-ACTION-PROTOCOL-MAP //= (
888	     zigbee: zigbee-action-map
889	   )

891	   zigbee-action-map = {
892	     endpointID: uint,
893	     clusterID: uint,
894	     commandID: uint,
895	     ? profileID: uint,
896	     ? manufacturerCode: uint,
897	   }

899	    Figure 19: CDDL definition for Zigbee Protocol Mapping for sdfAction

901	   Where:

903	   *  endpointID is the Zigbee endpoint ID that corresponds to the SDF
904	      action.

906	   *  clusterID is the Zigbee cluster ID that corresponds to the SDF
907	      action.

909	   *  commandID is the Zigbee command ID that corresponds to the SDF
910	      action.

912	   *  profileID has the same meaning and default as described for
913	      sdfProperty in Figure 17 (optional).

915	   *  manufacturerCode is the Zigbee manufacturer code of the command
916	      (optional).

918	   For example, a Zigbee protocol mapping to set a temperature:

920	   {
921	     "sdfAction": {
922	       "setTemperature": {
923	         "sdfProtocolMap": {
924	           "zigbee": {
925	             "profileID": 260,
926	             "endpointID": 1,
927	             "clusterID": 1026,
928	             "commandID": 0
929	           }
930	         }
931	       }
932	     }
933	   }
