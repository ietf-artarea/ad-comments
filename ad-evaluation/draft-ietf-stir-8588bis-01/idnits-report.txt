12	Abstract

14	   This document extends the Personal Assertion Token (PASSporT), which
15	   is a token object that conveys cryptographically signed information
16	   about the participants involved in communications.  The extension is
17	   defined based on the "Signature-based Handling of Asserted
18	   information using toKENs (SHAKEN)" specification by the ATIS/SIP
19	   Forum IP-NNI Task Group.  It provides both (1) a specific set of
20	   levels of confidence in the correctness of the originating identity
21	   of a call originated in a SIP-based telephone network as well as (2)
22	   an identifier that allows the Service Provider (SP) to uniquely
23	   identify the origin of the call within its network.  This document
24	   obsoletes RFC8588.

79	1.  Introduction

81	   The Signature-based Handling of Asserted information using toKENs
82	   (SHAKEN) [ATIS-1000074] specification defines a framework for using
83	   Secure Telephone Identity Revisited (STIR) protocols including the
84	   Personal Assertion Token (PASSporT) [RFC8225], SIP Authenticated
85	   Identity Management [RFC8224], and the STIR certificate framework
86	   [RFC8226] for implementing the cryptographic validation of an
87	   authorized originator of telephone calls using SIP.  Because the
88	   current telephone network contains traffic originated from both VoIP
89	   and TDM/SS7 (Time Division Multiplexing / Signaling System 7), there
90	   are many scenarios that need to be accounted for where PASSporT
91	   signatures may represent either direct or indirect call origination
92	   scenarios.  The SHAKEN [ATIS-1000074] specification defines levels of
93	   attestation of the origination of the call as well as an origination
94	   identifier that can help create a unique association between the
95	   origin of a particular call to the point in the VoIP or TDM telephone
96	   network the call came from to identify, for example, either a
97	   customer or class of service that call represents.  This document
98	   specifies these values as claims to extend the base set of PASSporT
99	   claims.

109	   In addition, the following terms are used in this document:

111	   *  Verified association: Typically defined as an authenticated
112	      relationship between a customer and a device that initiated a call
113	      on behalf of that customer, for example, a subscriber account with
114	      a specific SIM card or set of SIP credentials.

116	   *  PASSporT: Defined in [RFC8225] is a JSON Web Token [RFC7519]
117	      defined specifically for securing the identity of an initiator of
118	      personal communication.  This document defines a specific
119	      extension to PASSporT.

121	3.  Overview of "shaken" PASSporT Extension

123	   The SHAKEN framework is designed to use PASSporT [RFC8225] as a
124	   method of asserting the caller's telephone identity.  In addition to
125	   the PASSporT base claims, there are two additional claims that have
126	   been defined for the needs of a service provider to signal
127	   information beyond just the telephone identity.  First, in order to
128	   help bridge the transition of the state of the current telephone
129	   network (which has calls with no authentication and non-SIP [RFC3261]
130	   signaling not compatible with the use of PASSporT and Secure
131	   Telephone Identity (STI) in general), there is an attestation claim.
132	   This provides three levels of attestation: a full attestation when
133	   the service provider can fully attest to the calling identity, a
134	   partial attestation when the service provider originated a telephone
135	   call but cannot fully attest to the calling identity, and a gateway
136	   attestation, which is the lowest level of attestation and represents
137	   the service provider receiving a call from a telephone gateway that
138	   does not support PASSporT or STI.

140	   The second claim is a unique origination identifier that should be
141	   used by the service provider to identify different sources of
142	   telephone calls to support a traceback mechanism that can be used for
143	   enforcement and identification of a source of illegitimate calls.

145	   The use of the compact form of PASSporT is not specified in this
146	   document and is not specified for use in SHAKEN [ATIS-1000074].

148	   The next two sections define these new claims.

150	4.  PASSporT "attest" Claim

152	   This indicator allows for both identifying the service provider that
153	   is vouching for the call as well as clearly indicating what
154	   information the service provider is attesting to.  The "attest" claim
155	   can be one of the following three values: 'A', 'B', or 'C'.  These
156	   values correspond to 'Full Attestation', 'Partial Attestation', and
157	   'Gateway Attestation', respectively.  See [ATIS-1000074] for the
158	   definitions of these three levels of attestation.

160	5.  PASSporT "origid" Claim

162	   The purpose of the "origid" claim is described in [ATIS-1000074].
163	   The value of "origid" claim is a Universally Unique Identifier (UUID)
164	   as defined in [RFC9562].  Please refer to Section 10 for a discussion
165	   of the privacy considerations around the use of this value.

167	6.  Example "shaken" PASSporT

169	   Protected Header
170	   {
171	      "alg":"ES256",
172	      "typ":"passport",
173	      "ppt":"shaken",
174	      "x5u":"https://cert.example.org/passport.cer"
175	   }
176	   Payload
177	   {
178	      "attest":"A"
179	      "dest":{"tn":["12155550131"]}
180	      "iat":1443208345,
181	      "orig":{"tn":"12155550121"},
182	      "origid":"123e4567-e89b-12d3-a456-426655440000"
183	   }

185	7.  Using "shaken" in SIP

187	   The use of the "shaken" PASSporT type and the "attest" and "origid"
188	   claims for SIP is formally defined in [ATIS-1000074] using the SIP
189	   [RFC3261] Identity header field defined in [RFC8224].

191	8.  Order of Claim Keys

193	   The order of the claim keys MUST follow the rules of Section 9 of
194	   [RFC8225]; the claim keys MUST appear in lexicographic order.
195	   Therefore, the claim keys discussed in this document appear in the
196	   PASSporT Payload in the following order:

198	   *  attest

200	   *  dest

202	   *  iat

204	   *  orig

206	   *  origid

208	9.  Security Considerations

210	   This document defines a new PASSporT [RFC8225] extension.  The
211	   considerations related to the security of the PASSporT object itself
212	   are the same as those described in [RFC8225].

214	   [RFC8224] defines how to compare the values of the "dest", "orig",
215	   and "iat" claims against fields in a SIP message containing a
216	   PASSporT as part of validating that request.  The values of the new
217	   "attest" and "origid" claims added by this extension are not used in
218	   such a validation step.  They are not compared to fields in the SIP
219	   message.  Instead, they simply carry additional information from the
220	   signer to the consumer of the PASSporT.  This new information shares
221	   the same integrity protection and non-repudiation properties as the
222	   base claims in the PASSporT.

224	10.  Privacy Considerations

226	   As detailed in Section 26 of [RFC3261], SIP messages inherently carry
227	   identifying information of the caller and callee.  The addition of
228	   STIR cryptographically attests that the signing party vouches for the
229	   information given about the callee, as is discussed in the Privacy
230	   Considerations of [RFC8224].

232	   SHAKEN [ATIS-1000074] furthermore adds an "origid" value to the STIR
233	   PASSporT, which is an opaque unique identifier representing an
234	   element on the path of a given SIP request.  This identifier is
235	   generated by an originating telephone service provider to identify
236	   where within their network (e.g. a gateway or particular service
237	   element) a call was initiated; "origid" can facilitate forensic
238	   analysis of call origins when identifying and stopping bad actors
239	   trying to spoof identities or make fraudulent calls.

241	   The opacity of the "origid" claim value is intended to minimize
242	   exposure of information about the origination of calls labeled with
243	   an "origid" value.  It is therefore RECOMMENDED that implementations
244	   generate a unique "origid" value per call in such a way that only the
245	   generator of the "origid" can determine when two "origid" values
246	   represent the same or different elements.  If deployed systems
247	   instead use a common or related "origid" for service elements in
248	   their network, the potential for discovering patterns through
249	   correlation of those calls exists.  This could allow a recipient of
250	   calls to, for instance, learn that a set of callers are using a
251	   particular service or coming through a common gateway.  It is
252	   expected that SHAKEN PASSporTs are shared only within an [RFC3324]
253	   trust domain and will be stripped before calls exit that trust
254	   domain, but this information still could be used by analytics on
255	   intermediary and terminating systems to reveal information that could
256	   include geographic location and even device-level information,
257	   depending on how the "origid" is generated.
