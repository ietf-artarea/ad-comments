11	Abstract

13	   This document defines how to convert calendaring information between
14	   the JSCalendar and iCalendar data formats.  It considers every
15	   JSCalendar and iCalendar element registered at IANA at the time of
16	   publication.  It defines conversion rules for all elements that are
17	   common to both formats, as well as how convert arbitrary or unknown
18	   JSCalendar and iCalendar elements.  This document updates RFC 5545
19	   ("iCalendar") and jscalendarbis ("JSCalendar") by defining new
20	   properties and parameters for JSCalendar and iCalendar conversion.

170	1.2.  Scope and Goals

172	   This document outlines how to convert between the iCalendar [RFC5545]
173	   and JSCalendar [I-D.ietf-calext-jscalendarbis] data formats.  It
174	   describes which elements are common to both, but also highlights
175	   where the two formats differ.  For each common element, it defines a
176	   conversion rule and includes an example of how to convert that
177	   element.  All iCalendar and JSCalendar elements currently registered
178	   at IANA are in scope, but not all of these elements are common to
179	   both formats.

181	   For elements that have no counterpart in the other format, it is the
182	   goal of this document to define how to preserve them during
183	   conversion, but in general it is not the goal to achieve this by
184	   defining new standard elements.  Instead, this document updates
185	   [RFC5545] and [I-D.ietf-calext-jscalendarbis] by defining iCalendar
186	   and JSCalendar elements to preserve elements that have no equivalent
187	   in the other format.  These conversion-specific properties are
188	   defined in Section 4.1.2 for iCalendar, and Section 5.1.1 for
189	   JSCalendar.  Appendix A further outlines the discrepancies between
190	   the two formats.

192	1.3.  How to Read the Examples

194	   Later sections contain examples that illustrate how to convert
195	   between the iCalendar and JSCalendar data formats.  The notation of
196	   these examples is such that their main points should be clear to the
197	   reader, but their contents can also be parsed for automated testing.
198	   The following sections define the notation for such examples.

200	1.3.1.  iCalendar Examples

202	   An iCalendar example contains either an extract or a complete
203	   representation of iCalendar data.  It always represents an iCalendar
204	   object, even if the example only depicts non-VCALENDAR components or
205	   properties.  The following rules apply:

207	   *  An example that only contains iCalendar properties implicitly
208	      represents a VEVENT component having these properties set and that
209	      is part of a VCALENDAR component.

211	   *  An example that only contains one or more VEVENT, VTODO, VJOURNAL,
212	      FREEBUSY or VTIMEZONE components implicitly represents a VCALENDAR
213	      component that contains them.  An example that only contains one
214	      or more other components implicitly represents a VEVENT component
215	      having these components set and that is part of a VCALENDAR
216	      components.

218	   *  An example that only contains VEVENT or VTODO components
219	      implicitly represents a VCALENDAR component that contains them.

221	   *  An example that only contains a VCALENDAR component but no
222	      contained components implicitly represents a VCALENDAR component
223	      that contains a VEVENT component.

225	   *  Implicit components (those without a BEGIN and END, or omitted
226	      completely) are assumed to contain all mandatory properties with
227	      some value, but the actual value is irrelevant for the example.

229	   Figure 1 contains three examples, all of which represent the same
230	   iCalendar data.  In the first example, both the VEVENT component and
231	   VCALENDAR component are implicit.  In the second example, only the
232	   VCALENDAR component and its mandatory properties are implicit.  The
233	   third example depicts a complete VCALENDAR component, nothing is
234	   implicit.

358	1.4.  Lossy versus Lossless Conversion

360	   This document outlines how to convert iCalendar elements to
361	   JSCalendar elements, and the other way round.  Many of these can be
362	   represented by standard elements in both formats, meaning that they
363	   are registered in the iCalendar and JSCalendar IANA registries and
364	   differ from the special-purpose elements introduced in Section 4 and
365	   Section 5.  Still, a number of elements in either format have no
366	   standard counterpart in the other.  When converting between between
367	   iCalendar and JSCalendar, implementations MAY choose to only convert
368	   elements that have standard element in the target format, or aim to
369	   preserve as many elements as possible.

371	   When to choose between lossy and lossless conversion is
372	   implementation-specific.  For example:

374	   *  For lossy conversion, an implementation that internally stores
375	      calendar data in JSCalendar format might only want to convert to a
376	      subset of iCalendar elements for iMIP scheduling [RFC6047].  In
377	      this case, it might not make use any of the conversion-specific
378	      iCalendar properties introduced in Section 4.

380	   *  For lossless conversion, an implementation that internally stores
381	      calendar data in iCalendar format might want to convert without
382	      loss to JSCalendar when updating calendar events with JMAP
383	      [I-D.ietf-jmap-calendars].  For that, it can use the conversion-
384	      specific properties defined in Section 5.

386	   All the examples in this document illustrate lossless conversion, if
387	   not explicitly stated otherwise in the example.

514	2.1.2.  Recurring Components

516	   Components in an iCalendar object generally convert to distinct
517	   JSCalendar objects.  For example, two VEVENT components with
518	   different UID property values in the same iCalendar object convert to
519	   two separate Event objects in the Group object's entries.  As an
520	   exception to this rule, this does not apply to recurrence overrides,
521	   defined as follows.

523	   A VEVENT (or VTODO) component is a recurrence override if it has the
524	   RECURRENCE-ID property set, and the iCalendar object contains a
525	   VEVENT (or VTODO) component that does not have the RECURRENCE-ID but
526	   the RRULE property set, and the UID property values of the two
527	   components are equal.  The component without the RECURRENCE-ID
528	   property is in that case referred to as the "main component".

530	   The main component converts to an entry in the Group object's
531	   "entries" property.

533	   The recurrence override converts to the converted main component's
534	   "recurrenceOverrides" property.  Its RECURRENCE-ID property value
535	   converts to the key in the "recurrenceOverrides" property.  The value
536	   of the "recurrenceOverrides" property at that key is a PatchObject
537	   that transforms the converted main component into the converted
538	   recurrence override, but it MUST NOT contain any of the patches that
539	   are forbidden for the "recurrenceOverrides" property
540	   [I-D.ietf-calext-jscalendarbis] (Section 3.3.4).

542	   The following example illustrates how to convert a main component and
543	   its recurrence override:

637	2.1.3.  JSCalendar Ids

639	   JSCalendar generally uses JSON objects to represent a collection of
640	   same-typed values.  The keys are of type Id
641	   [I-D.ietf-calext-jscalendarbis] (Section 1.5.1), the values are
642	   JSCalendar object types.  If an iCalendar element converts to a value
643	   in such a collection then an implementation needs to choose an
644	   identifier as key.

646	   If the JSID parameter (Section 4.2.1) or JSID property
647	   (Section 4.1.1) is set on a property or component, then its value
648	   MUST be used as key when converting that element from iCalendar to
649	   JSCalendar.  In absence of the JSID parameter or property key
650	   generation is implementation-specific.

652	   Some sections later in this document describe key generation schemes
653	   for specific iCalendar elements by making use of UUID Version 5 with
654	   SHA1 hash [RFC9562] (Section 5.5).  The Namespace ID to generate such
655	   keys is "7f1e1965-ae73-4454-b088-232c90730ce2".  These key generation
656	   schemes are not mandatory, nor is making use of that particular
657	   Namespace ID when using UUID Version 5 (UUIDv5) as keys.

659	   Irrespective of the key generation scheme, all keys MUST be valid
660	   according to the definition of the Id type.  For consistency, keys
661	   SHOULD be stable such that converting the same iCalendar data to
662	   JSCalendar multiple times produces the same keys.

664	2.1.4.  Timezone identifiers

666	   Converting temporal properties such as DTSTART, DTEND, and
667	   RECURRENCE-ID requires to not only determine the date and time of the
668	   property value, but also the timezone it references.

670	   If the property value type is DATE [RFC5545] (Section 3.3.4) or
671	   DATE-TIME in FORM #1: DATE WITH LOCAL TIME [RFC5545] (Section 3.3.5)
672	   then the timezone is not set in JSCalendar.

674	   If the property value type is DATE-TIME in FORM #2: DATE WITH UTC
675	   TIME [RFC5545] (Section 3.3.5) then the timezone identifier is "Etc/
676	   UTC" in JSCalendar.

678	   If the property value type is DATE-TIME in FORM #3: DATE WITH LOCAL
679	   TIME AND TIME ZONE REFERENCE [RFC5545] (Section 3.3.5) then the
680	   timezone identifier is determined by the TZID parameter value as
681	   follows:

683	   If the TZID parameter value is equal to a name in the IANA Time Zone
684	   Database [TZDB] then the timezone identifier is that verbatim name.
685	   Otherwise, how to convert the TZID parameter value is implementation-
686	   specific: software libraries such as the International Components for
687	   Unicode (https://icu.unicode.org/) support converting Microsoft time
688	   zone names to IANA time zone identifiers.  Alternatively, an
689	   implementation might determine the name of an IANA time zone which
690	   has identical time zone rules over the time span of the calendar
691	   object.

693	   Implementations MAY preserve a TZID parameter set to a non-IANA
694	   timezone identifier and its related VTIMEZONE by use of the
695	   "convertedProperties" and "components" properties (see
696	   Section 5.1.1), but MUST NOT expect other implementations to consider
697	   them when processing the calendar object.

699	2.1.5.  DATE and DATE-TIME

701	   iCalendar provides the DATE and DATE-TIME value types to distinguish
702	   date-only from date-time values.  JSCalendar only supports date-time
703	   values.

705	   When converting from iCalendar to JSCalendar, a property value of
706	   type DATE-TIME converts to either a LocalDateTime or UTCDateTime,
707	   depending on the JSCalendar property definition.  A DATE value type
708	   converts to a LocalDateTime with zero time.

710	   Section 3.2 defines which iCalendar value type to choose when
711	   converting from JSCalendar to iCalendar.

4176	4.1.  New Properties

4178	4.1.1.  JSID

4180	   Property Name:
4181	      JSID

4183	   Purpose:
4184	      This property preserves the identifier of a JSCalendar object
4185	      value in iCalendar.

4187	   Value type:
4188	      TEXT; also see "Format Definition" below for value restrictions.

4190	   Property Parameters:
4191	      IANA and non-standard property parameters can be specified on this
4192	      property.

4194	   Conformance:
4195	      This property can be specified at most once in any calendar
4196	      component.

4198	   Description:
4199	      This property specifies the JSON object key of the JSCalendar
4200	      object to which an iCalendar component converts to.  For example,
4201	      this property set in a VALARM component within a VEVENT component
4202	      defines the key of the Alert object in the Event object's "alerts"
4203	      property (see Figure 87).

4205	      The value of the JSID property MUST be a valid object key
4206	      according to the definition of the JSCalendar property to which
4207	      the component converts to.

4209	   Format Definition:
4210	      This property is defined by the following notation:

4212	      jsid-prop = "JSID" *(";" other-param) ":" TEXT CRLF

4214	   Example(s):
4215	      The following example illustrates how to convert the JSID property
4216	      set in a VALARM component.

4218	      BEGIN:VEVENT
4219	      ...
4220	      BEGIN:VALARM
4221	      UID:52DFB000-3C49-4577-8003-3086001BD26A
4222	      JSID:myalert
4223	      ...
4224	      END:VALARM
4225	      "@type": "Event",
4226	      "alerts": {
4227	        "myalert": {
4228	          "@type": "Alert",
4229	          "iCalendar": {
4230	            "@type": "ICalComponent",
4231	            "name": "valarm",
4232	            "properties": [
4233	              [
4234	                "uid",
4235	                {},
4236	                "text",
4237	                "52DFB000-3C49-4577-8003-3086001BD26A"
4238	              ]
4239	            ]
4240	          },
4241	          "...": ""
4242	        }
4243	      }

4245	        Figure 87: Converting the JSID property of a VALARM component

4247	4.1.2.  JSPROP

4249	   Property Name:
4250	      JSPROP

4252	   Purpose:
4253	      This property represents a JSCalendar property in iCalendar.

4255	   Value type:
4256	      TEXT; also see "Format Definition" below for value restrictions.

4258	   Property Parameters:
4259	      The JSPTR parameter (Section 4.2.2) MUST be specified on this
4260	      property.  Other IANA and non-standard property parameters can be
4261	      specified on this property.

4263	   Conformance:
4264	      This property can be specified multiple times in any calendar
4265	      component.

4267	   Description:
4268	      This property converts an arbitrary JSCalendar property from and
4269	      to iCalendar.  The iCalendar property value is the JSON-encoded
4270	      value of the JSCalendar property, represented as a TEXT value.
4271	      The JSON value MUST NOT be the null value, and it SHOULD NOT
4272	      contain insignificant whitespace as defined in Section 2 of
4273	      [RFC8259].  The value of the JSPTR parameter points to the
4274	      JSCalendar property within the JSCalendar object and MUST NOT
4275	      start with the SOLIDUS (U+002F) character.  The pointer MUST NOT
4276	      reference into an array.

4278	      All JSPROP properties in a calendar component together form a
4279	      PatchObject [I-D.ietf-calext-jscalendarbis] (Section 1.5.9): the
4280	      JSPTR parameter of a JSPROP property corresponds to a key in the
4281	      PatchObject, the property value corresponds to the JSON value for
4282	      that key.  When converting from iCalendar to JSCalendar, the
4283	      PatchObject MUST only be applied after all other iCalendar
4284	      elements of the component have been converted.  Only new
4285	      properties are allowed to be set, a JSON pointer in the
4286	      PatchObject that points to an existing property MUST be ignored.

4288	   Format Definition:
4289	      This property is defined by the following notation:

4291	      jsprop = "JSPROP" jsprop-param ":" TEXT CRLF

4293	      jsprop-param  = *(
4294	                ; The following are MANDATORY and MUST NOT
4295	                ; occur more than once
4296	                ( ";" jsptr-param )
4297	                ;
4298	                ; The following is OPTIONAL
4299	                ; and MAY occur more than once.
4300	                ;
4301	                (";" other-param)
4302	                ;
4303	                )

4305	   Example(s):

4307	      The following example illustrates how to convert a JSPROP property
4308	      with a JSON boolean value

4310	      JSPROP;JSPTR="example.com:foo":true
4311	      "example.com:foo": true

4313	        Figure 88: Converting the JSPROP property with a JSON boolean
4314	                                    value

4316	      The following example illustrates how to convert a JSPROP property
4317	      with a JSON object value

4319	      JSPROP;JSPTR="example.com:foo":{"bar":1234\,"baz":"bam"}
4320	      "example.com:foo": {
4321	        "bar": 1234,
4322	        "baz": "bam"
4323	      }

4325	      Figure 89: Converting the JSPROP property with a JSON object value

4327	      The following example illustrates how to convert a JSPROP property
4328	      that points to a property within a JSCalendar Alert.  The JSON
4329	      pointer in the JSPTR parameter is relative to the Alert object.

4331	      BEGIN:VEVENT
4332	      ...
4333	      BEGIN:VALARM
4334	      JSPROP;JSPTR="example.com:foo":"bar"
4335	      ...
4336	      END:VALARM
4337	      "@type": "Event",
4338	      "alerts": {
4339	        "DB7A8058-2212-46D9-87C2-867C7F65D625": {
4340	          "@type": "Alert",
4341	          "example.com:foo": "bar",
4342	          "...": ""
4343	        }
4344	      }

4346	          Figure 90: Converting the JSPROP property within a VALARM
4347	                                  component

4351	      pointer in the JSPTR parameter is relative to the Event object

4353	      JSID parameter (Section 4.2.1) on the ATTACH property ensures that
4354	      the JSON path remains valid during conversion.

4356	      BEGIN:VEVENT
4357	      ...
4358	      ATTACH;JSID=mylink1:https://www.rfc-editor.org/rfc/rfc8984.html

4377	   Parameter Name:
4378	      JSID

4380	   Format Definition:
4381	      jsid-param  = "JSID" "=" param-value

4383	   Description:
4384	      This parameter specifies the JSON object key of the JSCalendar

4408	   Parameter name:
4409	      JSPTR

4411	   Purpose:
4412	      To specify a pointer to a JSCalendar property.

4415	      This parameter is set on a JSPROP (Section 4.1.2) property.  Its

4431	5.1.  New Properties

4433	5.1.1.  iCalendar

4435	   Name:
4436	      iCalendar

4438	   Context:
4439	      Any JSCalendar object

4441	   Type:
4442	      ICalComponent (optional)

4444	   Description
4445	      This property contains information about iCalendar data that got
4446	      converted to this JSCalendar object.  It allows for preserving the
4447	      name of iCalendar elements, such as a component's name, properties
4448	      and subcomponents.  This specification defines the ICalComponent
4449	      object type for converting iCalendar components to a JSCalendar
4450	      object.  Future specifications MAY define additional value types
4451	      for this property.

4453	      An ICalComponent object has the following properties:

4455	      @type: String  This specifies the type of this object.  This MUST
4456	         be "ICalComponent", if set.

4458	      name: String (mandatory)  This is the name of the iCalendar
4459	         component in lowercase.

4461	      components: *[][] (optional)  This contains subcomponents of the
4462	         iCalendar component which did not convert to standard
4463	         JSCalendar elements.  The value MUST be a list of iCalendar
4464	         components formatted in jCal as defined in Section 3.3 of
4465	         [RFC7265].

4467	      convertedProperties: String[ICalProperty] (optional)  This
4468	         contains conversion-related information about the component's
4469	         properties that got partially or fully converted to JSCalendar.
4470	         Each key defines the path to a JSCalendar element.  The value
4471	         for each key contains information about the iCalendar property
4472	         which converted to the JSCalendar element located at that key.
4473	         Unless otherwise defined for a specific iCalendar property, the
4474	         path points to the JSCalendar property that the iCalendar
4475	         property value converts to.

4477	         The key MUST be a valid key of a PatchObject as defined in
4478	         Section 1.5.9 of [I-D.ietf-calext-jscalendarbis].  The key MAY
4479	         point to the key in a nested object if the element at that key
4480	         was converted from an iCalendar property of the component for
4481	         which the "iCalendar" property is set.  It MUST NOT point into
4482	         nested objects otherwise.

4484	      properties: *[][] (optional)  This contains properties of the
4485	         iCalendar component which did not convert to standard
4486	         JSCalendar elements.  The value MUST be a list of iCalendar
4487	         properties formatted in jCal as defined in Section 3.4 of
4488	         [RFC7265].

4490	      An ICalProperty object has the following properties:

4492	      @type: String  This specifies the type of this object.  This MUST
4493	         be "ICalProperty", if set.

4495	      name: String (mandatory)  This is the name of the iCalendar
4496	         property in lowercase.

4498	      valueType: String (optional)  This is the name of the iCalendar
4499	         property value type in lowercase.

4501	      parameters: String[String|String[]] (optional)  This contains
4502	         parameters of the iCalendar property.  The value MUST comply
4503	         with iCalendar parameters formatted in jCal as defined in
4504	         Section 3.5 of [RFC7265].

4506	   The example in Figure 93 describes how to convert unknown iCalendar
4507	   elements to the "iCalendar" property.  The X-FOO parameter set on the
4508	   SUMMARY property illustrates how to preserve an unknown iCalendar
4509	   parameter on a property that does convert to a standard JSCalendar
4510	   element.  The X-BAR property and X-BAZ component illustrate how to
4511	   convert entirely unknown iCalendar elements.

4513	   BEGIN:VEVENT
4514	   SUMMARY;X-FOO=bar:test
4515	   ...
4516	   X-BAR:bam
4517	   ...
4518	   BEGIN:X-BAZ
4519	   UID:507A08F9-81D8-4D16-9480-D6D75E977943
4520	   END:X-BAZ
4521	   ...

4523	   {
4524	     "@type": "Event",
4525	     "title": "test",
4526	     "iCalendar": {
4527	       "@type": "ICalComponent",
4528	       "name": "vevent",

4536	         }

4544	         ]

4547	         [

4551	               "uid",

4824	   This section highlights iCalendar and JSCalendar elements for which

4827	   this document.

4830	   example using the properties defined in Section 4 and Section 5, or

4833	   register them at IANA, either extending this list of inconvertible
4834	   elements, or rather reduce it by introducing a standard element to
4835	   convert to.
