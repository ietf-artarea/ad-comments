106	1.  Introduction

108	   The Lightweight Directory Access Protocol (LDAP) directory defines
109	   several data types which specify the syntax definitions of
110	   attributes.  These are identified by ASN.1 OBJECT IDENTIFIER types.
111	   Furthermore, these syntax definitions can be used to uniquely
112	   identify data types as character representations in other
113	   applications.  Some widely used syntax specifications are missing
114	   from the initial LDAP specification.  This document provides
115	   additional syntax definitions that have been registered and may be
116	   used by application providers.

118	1.1.  Conventions

120	   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
121	   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
122	   "OPTIONAL" in this document are to be interpreted as described in BCP
123	   14 [RFC2119] [RFC8174] when, and only when, they appear in all
124	   capitals, as shown here.

126	   Some of the syntax definitions are defined according to the regular
127	   expressions defined in [RFC9485].

129	2.  Syntaxes

131	   The following additional syntaxes and their associated descriptions
132	   and OBJECT IDENTIFIER types are defined.

134	2.1.  ASN.1 Syntax Definitions

136	   The following additional syntaxes are defined and are based on
137	   [ASN.1].

139	2.1.1.  Date

141	   The Date type represents a date in the Gregorian calendar.  It is
142	   defined as a useful TIME type in [ASN.1] and conforms to the extended
143	   format syntax of a calendar date as defined in [ISO.8601.2004].

145	   A Date value SHALL be written using the following syntax: YYYY-MM-DD
146	   where YYYY represents a year between 1582 and 9999, MM the month
147	   value from 01 to 12 and DD a day in the month from 01 to 31.

149	   Examples:

151	   *  9999-02-25

153	   *  1583-01-31

155	   The LDAP definition for the Date syntax is:

157	   *  ( 1.3.6.1.4.1.61799.5.40.31 DESC 'Date' )

159	   This syntax corresponds to the DATE ASN.1 type from [ASN.1].

161	2.1.2.  Date-Time

163	   The Date-time type represents a date and local time using a 24 hour
164	   clock.  It is defined as a useful TIME type in [ASN.1] and conforms
165	   to the extended format syntax of a date and time without any timezone
166	   specifier as defined in [ISO.8601.2004].

168	   A Date-Time value SHALL be written using the following syntax: YYYY-
169	   MM-DDThh:mm:ss where YYYY represents a year between 1582 and 9999, MM
170	   the month value from 01 to 12, DD a day in the month from 01 to 31,
171	   hh the hour from 00 to 24, mm the minute from 00 to 59, and ss the
172	   seconds with allowed values of 00 to 60 where 60 represents a leap
173	   second.

175	   Examples:

177	   *  1583-01-01T00:59:59

179	   *  1975-01-19T23:45:34

181	   The LDAP definition for the Date-Time syntax is:

183	   *  ( 1.3.6.1.4.1.61799.5.40.33 DESC 'Date-Time' )

185	   This syntax corresponds to the DATE-TIME ASN.1 type from [ASN.1].

187	2.1.3.  Duration

189	   The Duration type represents an elapsed time with a resolution of up
190	   to a fractions of seconds.  It is defined as a useful TIME type in
191	   [ASN.1] and conforms to a subset of the extended format syntax of a
192	   time interval by duration as defined in [ISO.8601.2004].

194	   A duration syntax value SHALL conform to the following regular
195	   expression, and additionally at least one component designator and
196	   its associated valueSHALL be present (i.e., the strings "P" and "PT"
197	   are not valid Duration values):

199	   P([0-9]+Y)?([0-9]+M)?([0-9]+D)?(T([0-9]+H)?([0-9]+M)?([0-9]+(\.[0-9]{1,3})?S)?)?

201	   If the number of years, months, days, hours, minutes, or seconds in
202	   any expression equals zero, the number and its corresponding
203	   designator MAY be omitted.  However, at least one number and its
204	   designator SHALL be present.

206	   Examples:

208	   *  P29M0D -- 29 months, 0 days to an accuracy of 1 day.

210	   *  P29MT0S -- 29 months, 0 days, 0 hours, 0 minutes, 0 seconds, to an
211	      accuracy of 1 second.

213	   *  PT3445.5S -- 3445.5 seconds

215	   The LDAP definition for the Duration syntax is:

217	   *  ( 1.3.6.1.4.1.61799.5.40.34 DESC 'Duration' )

219	   This syntax corresponds to a very strict subset of the DURATION ASN.1
220	   type from [ASN.1], in that the order of parameters need to be
221	   respected and fractional values SHALL only apply to the seconds
222	   designation and when present, are limited up to 3 digits (millisecond
223	   precision).

225	2.1.4.  Real

227	   The Real type represents the computational approximations to the
228	   mathematical "real number".  The format for the Real is as defined in
229	   Section 21 of [ASN.1].

231	   A Real syntax value SHALL conform to the following regular
232	   expression:

234	   ([-]?[0-9]+(\.[0-9]+)?([E][-]?[0-9]+)?)|PLUS-INFINITY|MINUS-INFINITY|NOT-A-NUMBER

236	   Examples:

238	   *  3.14159

240	   *  MINUS-INFINITY
241	   *  0

243	   *  -5.3E4 -- Equal to -53000

245	   *  5E3 -- 5000

247	   The LDAP definition for the Real syntax is:

249	   *  ( 1.3.6.1.4.1.61799.5.40.9 DESC 'Real' )

251	   This syntax corresponds to a subset of the REAL ASN.1 type from
252	   [ASN.1] where the sequence syntax is not allowed, the values are
253	   limited to base ten, where a digit before the decimal point is
254	   required, where only the character 'E' is allowed to specify the
255	   exponent, where the preceding optional "+" sign is prohibited in both
256	   the mantissa and the exponent, and where leading zeros in the integer
257	   part SHALL NOT be present unless the integer part is "0".

259	2.1.5.  Time Of Day

261	   The Time Of Day type represents a local time using a 24 hour clock.
262	   It is defined as a useful TIME type in [ASN.1] and conforms to the
263	   extended format syntax of a local time as defined in [ISO.8601.2004].

265	   A Time Of Day value SHALL be written using the following syntax:
266	   hh:mm:ss where hh represents the hour from 00 to 24, mm represents
267	   the minute from 00 to 59, and ss represents the seconds with allowed
268	   values of 00 to 60 where 60 represents a leap second.

270	   Examples for Time Of Day:

272	   *  00:59:59

274	   *  01:45:54

276	   The LDAP definition for the Time Of Day syntax is:

278	   *  ( 1.3.6.1.4.1.61799.5.40.32 DESC 'Time Of Day' )

280	   This syntax corresponds to the TIME-OF-DAY ASN.1 type from [ASN.1].

282	2.1.6.  Visible String

284	   The Visible String type represents a character repertoire that
285	   contains the printable ASCII character set (in the Unicode range
286	   U+0020 to U+007E).  It is defined in [ASN.1].

288	   This syntax value SHALL conform to the following regular expression:

290	   [0-9A-Za-z !"#$%&'()*+,\-./:;<=>?@\[\\\]^_`{|}~]*

292	   Examples:

294	   *  hello world

296	   *  (x+y)=z

298	   The LDAP definition for the Visible String syntax is:

300	   *  ( 1.3.6.1.4.1.61799.5.40.26 DESC 'Visible String' )

302	   This syntax corresponds to the VisibleString ASN.1 type from [ASN.1].

304	2.2.  Constrained ASN.1 Syntax Definitions

306	   The following additional syntaxes are defined as constraints of basic
307	   ASN.1 types that may be used to be more precise in encoding and input
308	   validation.

310	2.2.1.  Float32

312	   The Float32 type represents a real number which fits in the range of
313	   a [IEEE_754_2019] single precision floating point value.

315	   The Float32 syntax follows the base 10 syntax of the real type (See
316	   Section 2.1.4) with a constrained range.  For equality matching
317	   purposes, negative zero SHALL be considered equal to positive zero
318	   and NOT-A-NUMBER SHALL NOT be considered equal to any value,
319	   including itself.

321	   Examples:

323	   *  3.14159 -- value will be rounded to the nearest representable
324	      value

326	   *  MINUS-INFINITY

328	   *  -5.3E4 -- Equal to -53000

330	   The LDAP definition for the Float32 type syntax is:

332	   *  ( 1.3.6.1.4.1.61799.5.40.9.4 DESC 'Float32' )

334	   This syntax corresponds to the following ASN.1 type from [ASN.1]:

336	   Float32 ::= REAL (WITH COMPONENTS {
337	     mantissa (-16777215..16777215),
338	     base (2),
339	     exponent (-149..104) })

341	2.2.2.  Float64

343	   The Float64 type represents a real number which fits in the range of
344	   a [IEEE_754_2019] double precision floating point value.

346	   The Float64 syntax follows the base 10 syntax of the real type (See
347	   Section 2.1.4) with a constrained range.  For equality matching
348	   purposes, negative zero SHALL be considered equal to positive zero
349	   and NOT-A-NUMBER SHALL NOT be considered equal to any value,
350	   including itself.

352	   Examples:

354	   *  3.1415926535897932 -- value will be rounded to the nearest
355	      representable value

361	   The LDAP definition for the Float64 type syntax is:

542	2.3.  Other Syntax Definitions

544	   The following additional syntaxes are defined and are based on IETF
545	   RFC's, or other international standards.

547	2.3.1.  Language

549	   A language provides a representation of a spoken or written language
550	   as well as an optional region and other specifiers.  The exact syntax
551	   allowed is defined in Section 2 of [RFC5646].

553	   A Language syntax value SHALL conform to the following regular
554	   expression:

556	   ([a-zA-Z]{2,8}|x-[a-zA-Z0-9]{1,8})(-[a-zA-Z0-9]{1,8})*

558	   The regular expression provides a structural check only.  Conformance
559	   to the full syntax defined in [RFC5646] is additionally required.

561	   Examples:

563	   *  en

565	   *  fr-CA

567	   The LDAP definition for the Language syntax is:

569	   *  ( 1.3.6.1.4.1.61799.5.40.19.1 DESC 'Language' )

571	   This syntax corresponds to the following ASN.1 type from [ASN.1]:

573	   Language ::= PrintableString (PATTERN "([a-zA-Z]#(2,8)|x-[a-zA-Z0-9]#(1,8))(-[a-zA-Z0-9]#(1,8))*")

1039	2.3.10.  Time Of Day with Timezone

1041	   The Time Of Day with Timezone syntax type represents a time with
1042	   explicit timezone information using a 24 hour clock.  It is defined
1043	   as a TIME type in [ASN.1] and conforms to the extended format syntax
1044	   of a time either represented as a local time followed by a UTC offset
1045	   or as a UTC time indicated by the 'Z' designator, as defined in
1046	   [ISO.8601.2004].

1048	   A Time Of Day with Timezone value SHALL be written using the
1049	   following syntax: hh:mm:ss where hh represents the hour from 00 to
1050	   24, mm represents the minute from 00 to 59, and ss represents the
1051	   seconds with allowed values of 00 to 60 where 60 represents a leap
1052	   second followed by a timezone indicator.

1054	   The timezone indicator is in the form +hh:mm where hh represents the
1055	   number of hours and mm the number of minutes if the local time is
1056	   ahead of or equal to UTC time.  The timezone indicator is -hh:mm if
1057	   the local time is behind UTC time.  If the time represents an UTC
1058	   time, the time shall be followed without space, by the timezone UTC
1059	   designator [Z].  This standard supports time differences in the range
1060	   –15 hours to +15 hours to align with [ASN.1].

1062	   Examples:

1064	   *  00:59:59Z

1066	   *  01:45:54-01:00

1068	   The LDAP definition for the Time Of Day with Timezone syntax is:

1070	   *  ( 1.3.6.1.4.1.61799.5.40.35 DESC 'Time Of Day with Timezone' )

1072	   This syntax corresponds to a subset of the TIME ASN.1 type from
1073	   [ASN.1] with the specified configuration:

1075	   Time-with-timezone ::=
1076	     TIME((SETTINGS "Basic=Time Time=HMS Local-or-UTC=LD")|
1077	          (SETTINGS "Basic=Time Time=HMS Local-or-UTC=Z"))

1079	3.  Matching rules

1081	   This section defines matching rules for syntaxes that require
1082	   comparison semantics beyond simple string matching.  Syntaxes not
1083	   listed here use existing matching rules from [RFC4517]: integer types
1084	   (Int8, Int16, Int32, Int64, UInt8, UInt16, UInt32, UInt64,
1085	   Percentage) use integerMatch and integerOrderingMatch; string types
1086	   (Text, Normalized String, Token, Visible String, NCName, Qualified
1087	   Name) use caseExactMatch; Language and Media Type use
1088	   caseIgnoreMatch; and Date and Date-Time use caseExactMatch and
1089	   caseExactOrderingMatch.

1091	3.1.  uriMatch

1093	   The uriMatch rule compares for equality a presented value with an
1094	   attribute value of type URI (Section 2.3.4).

1096	   The comparison is done using syntax-based normalization as defined in
1097	   Section 6.2.2 of [RFC3986].

1099	   The LDAP definition for the uriMatch rule is:

1101	   *  ( 1.3.6.1.4.1.61799.5.13.26.4 NAME 'uriMatch' SYNTAX
1102	      1.3.6.1.4.1.61799.5.40.26.4 )

1104	   The rule returns TRUE if the attribute value represents the same URI
1105	   as the presented value.

1107	3.2.  openDateMatch

1109	   The openDateMatch rule compares for equality a presented value with
1110	   an attribute value of type OpenDate (Section 2.3.3).

1112	   For comparison purposes, OpenDate values SHALL first be normalized to
1113	   a full date-time in UTC timezone using the following rules:

1115	   1.  If the month component is absent it is assumed to be one.

1117	   2.  If the day component is absent it is assumed to be one.

1119	   3.  If the hours component is absent it is assumed to be zero.

1121	   4.  If the minutes component is absent it is assumed to be zero.

1123	   5.  If the seconds component is absent it is assumed to be zero.

1125	   6.  If the decimal fraction component is absent it is assumed to be
1126	       zero.

1128	   7.  If a timezone is present the date and time is normalized to the
1129	       UTC timezone.

1131	   8.  If no timezone is present it is assumed, by convention, to be in
1132	       the UTC timezone.

1134	   9.  If the time component indicates a value of 24:00:00 it is
1135	       replaced by 00:00:00 and the day is incremented by one.

1137	   This normalization procedure is inspired by, but not identical to,
1138	   the implicit timezone and value comparison rules defined in
1139	   Section 9.4 of [W3C.xpath-functions-31].  After normalization, values
1140	   are compared chronologically.

1142	   The LDAP definition for the openDateMatch rule is:

1144	   *  ( 1.3.6.1.4.1.61799.5.13.14.1 NAME 'openDateMatch' SYNTAX
1145	      1.3.6.1.4.1.61799.5.40.14.1 )

1147	   The rule returns TRUE if the attribute value represents the same
1148	   OpenDate as the presented value.

1150	3.3.  openDateOrderingMatch

1152	   The openDateOrderingMatch rule compares the ordering a presented
1153	   value with an attribute value of type OpenDate (Section 2.3.3).

1155	   Values are first normalized using the algorithm in Section 3.2.  The
1156	   normalized values are then compared chronologically.

1158	   The LDAP definition for the openDateOrderingMatch rule is:

1160	   *  ( 1.3.6.1.4.1.61799.5.13.14.1.1 NAME 'openDateOrderingMatch'
1161	      SYNTAX 1.3.6.1.4.1.61799.5.40.14.1 )

1163	   The rule returns TRUE if the attribute value represents an OpenDate
1164	   which is earlier than the presented OpenDate.

1166	3.4.  timeMatch

1168	   The timeMatch rule compares for equality a presented value with an
1169	   attribute value of type Time Of Day (Section 2.1.5).

1171	   Values are compared component by component (hours, minutes, seconds)
1172	   in order of significance.  A time value of 24:00:00 is considered end
1173	   of day, and is therefore not equal to 00:00:00.

1175	   The LDAP definition for the timeMatch rule is:

1177	   *  ( 1.3.6.1.4.1.61799.5.13.32 NAME 'timeMatch' SYNTAX
1178	      1.3.6.1.4.1.61799.5.40.32 )

1180	   The rule returns TRUE if the attribute value represents the same Time
1181	   Of Day as the presented value.

1183	3.5.  timeOrderingMatch

1185	   The timeOrderingMatch rule compares the ordering of a presented value
1186	   with an attribute value of type Time Of Day (Section 2.1.5).

1188	   Values are compared component by component (hours, minutes, seconds)
1189	   in order of significance.  A time value of 24:00:00 is considered end
1190	   of day, and is therefore greater than 00:00:00.

1192	   The LDAP definition for the timeOrderingMatch rule is:

1194	   *  ( 1.3.6.1.4.1.61799.5.13.32.1 NAME 'timeOrderingMatch' SYNTAX
1195	      1.3.6.1.4.1.61799.5.40.32 )

1197	   The rule returns TRUE if the attribute value represents a Time Of Day
1198	   which is earlier than the presented Time Of Day.

1200	3.6.  timeWithTZMatch

1202	   The timeWithTZMatch rule compares for equality a presented value with
1203	   an attribute value of type Time Of Day with Timezone
1204	   (Section 2.3.10).

1206	   Before comparison, both values are normalized to UTC.  During
1207	   normalization, a time value of 24:00:00 is replaced with 00:00:00.
1208	   After normalization, values are equal if and only if their hours,
1209	   minutes and seconds components are identical.

1211	   The LDAP definition for the timeWithTZMatch rule is:

1213	   *  ( 1.3.6.1.4.1.61799.5.13.35 NAME 'timeWithTZMatch' SYNTAX
1214	      1.3.6.1.4.1.61799.5.40.35 )

1216	   The rule returns TRUE if the attribute value represents the same Time
1217	   Of Day with Timezone as the presented value.

1219	3.7.  timeWithTZOrderingMatch

1221	   The timeWithTZOrderingMatch rule compares the ordering of a presented
1222	   value with an attribute value of type Time Of Day with Timezone
1223	   (Section 2.3.10).

1225	   Before comparison, both values are normalized to UTC.  During
1226	   normalization, a time value of 24:00:00 is replaced with 00:00:00.
1227	   After normalization, values are compared component by component
1228	   (hours, minutes, seconds) in order of significance.

1230	   The LDAP definition for the timeWithTZOrderingMatch rule is:

1232	   *  ( 1.3.6.1.4.1.61799.5.13.35.1 NAME 'timeWithTZOrderingMatch'
1233	      SYNTAX 1.3.6.1.4.1.61799.5.40.35 )

1235	   The rule returns TRUE if the attribute value represents a Time Of Day
1236	   with Timezone which is earlier than the presented Time Of Day with
1237	   Timezone.

1239	3.8.  realMatch

1241	   The realMatch rule compares for equality a presented value with an
1242	   attribute value of type Real (Section 2.1.4).

1244	   This matching rule also applies to the Float32 and Float64 syntaxes,
1245	   which are constrained subsets of the Real syntax.

1247	   Values are compared by their mathematical value.  NOT-A-NUMBER is not
1248	   equal to any value, including itself.  Negative zero is equal to
1249	   positive zero.  MINUS-INFINITY is equal only to itself, and PLUS-
1250	   INFINITY is equal only to itself.

1252	   The LDAP definition for the realMatch rule is:

1254	   *  ( 1.3.6.1.4.1.61799.5.13.9 NAME 'realMatch' SYNTAX
1255	      1.3.6.1.4.1.61799.5.40.9 )

1257	   The rule returns TRUE if the attribute value represents the same Real
1258	   value as the presented value.

1260	3.9.  realOrderingMatch

1262	   The realOrderingMatch rule compares the ordering of a presented value
1263	   with an attribute value of type Real (Section 2.1.4).

1265	   This matching rule also applies to the Float32 and Float64 syntaxes,
1266	   which are constrained subsets of the Real syntax.

1268	   MINUS-INFINITY is less than all finite values and PLUS-INFINITY is
1269	   greater than all finite values.  Negative zero is equal to positive
1270	   zero for ordering purposes.  NOT-A-NUMBER is greater than all other
1271	   values, including PLUS-INFINITY.  All NOT-A-NUMBER values are
1272	   considered equal for ordering purposes.

1274	   Note: IEEE-754 [IEEE_754_2019] arithmetic comparison leaves NOT-
1275	   A-NUMBER unordered with respect to all values.  This rule instead
1276	   assigns NOT-A-NUMBER a conventional position to ensure a total
1277	   ordering, which is required for consistent indexing, sorting, and
1278	   evaluation of inequality filters by directory implementations.

1280	   The LDAP definition for the realOrderingMatch rule is:

1282	   *  ( 1.3.6.1.4.1.61799.5.13.9.1 NAME 'realOrderingMatch' SYNTAX
1283	      1.3.6.1.4.1.61799.5.40.9 )

1285	   The rule returns TRUE if the attribute value is less than the
1286	   presented value.

1288	3.10.  durationMatch

1290	   The durationMatch rule compares for equality a presented value with
1291	   an attribute value of type Duration (Section 2.1.3).

1293	   Two duration values are equal if and only if they represent the same
1294	   total number of months and the same total number of milliseconds,
1295	   where:

1297	   *  Total months is (years x 12) + months.

1299	   *  Total milliseconds is (days x 86400000) + (hours x 3600000) +
1300	      (minutes x 60000) + (seconds x 1000) + milliseconds.

1302	   Note that month components and day-time components are compared
1303	   independently and are never converted into each other.  Consequently,
1304	   a duration such as P1M (one month) is never equal to P30D (thirty
1305	   days), even though they may represent the same elapsed time for
1306	   certain dates.  This behavior is intentional and consistent with the
1307	   abstract definition of duration.

1309	   Implementations SHOULD use integer arithmetic for these computations
1310	   to avoid floating-point precision issues.

1312	   The LDAP definition for the durationMatch rule is:

1314	   *  ( 1.3.6.1.4.1.61799.5.13.34 NAME 'durationMatch' SYNTAX
1315	      1.3.6.1.4.1.61799.5.40.34 )

1317	   The rule returns TRUE if the attribute value represents the same
1318	   duration as the presented value.

1447	5.  Security Considerations

1449	   When interpreting security-sensitive fields (in particular, fields
1450	   used to grant or deny access), implementations MUST ensure that any
1451	   matching rule comparisons are done on the underlying abstract value,
1452	   regardless of the particular encoding used.

1454	5.1.  Text, Normalized String and Token

1456	   The Text, Normalized String, and Token syntaxes have been defined for
1457	   general textual information.  For this reason, and for forward
1458	   compatibility with future versions of the Unicode Standard, the
1459	   prohibited code points have been kept to a minimum.

1461	   These syntaxes permit Unicode format characters (General_Category Cf)
1462	   because they are required for the correct representation of text in
1463	   several scripts.  However, some format characters may pose security
1464	   risks when values are displayed or compared without appropriate
1465	   normalization.  Applications MAY impose additional restrictions on
1466	   permitted code points as a matter of local policy.

1468	   These syntaxes SHOULD NOT be used for security-sensitive attributes
1469	   such as identifiers, group names, or access control labels.  The
1470	   NCName (Section 2.3.5) or Qualified Name (Section 2.3.6) syntaxes
1471	   SHOULD be used for such purposes instead.

1473	   Text, Normalized String, and Token values SHOULD be matched and
1474	   compared according to specific comparison rules, such as those
1475	   defined in [RFC4518] or the PRECIS OpaqueString profile ([RFC8265]).
