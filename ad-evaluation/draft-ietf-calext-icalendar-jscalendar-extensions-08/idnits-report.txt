11	Abstract

13	   This document defines a set of new elements for iCalendar and extends
14	   the use of existing ones.  Their main purpose is to extend the
15	   semantics of iCalendar with elements defined in JSCalendar, but the
16	   new definitions also aim to be useful within just the iCalendar
17	   format.  This document updates RFC 5545 ("iCalendar") and its
18	   extension documents RFC 7986 and RFC 9073.

76	1.  Introduction

78	   The JSCalendar [I-D.ietf-calext-jscalendarbis] format aims to be an
79	   alternative to the iCalendar [RFC5545] format for representation of
80	   calendaring data.  It introduces new semantics that are not covered
81	   in the current definition of iCalendar and its various extensions.
82	   Converting calendaring data between the two formats is defined in
83	   [I-D.ietf-calext-jscalendar-icalendar] with the goal of not losing
84	   any semantics during conversion.  To achieve this, this document
85	   defines new iCalendar elements and extends existing definitions.  To
86	   do so, it follows the recommendations for introducing new iCalendar
87	   elements as specified in Section 3 of [RFC7986].  This document
88	   updates the definitions of the GEO property [RFC5545]
89	   (Section 3.8.1.6), the COLOR property [RFC7986] (Section 5.9) and the
90	   VLOCATION component [RFC9073] (Section 7.2).

107	2.  Updated Properties

109	2.1.  GEO Property

111	   This specification deprecates the "GEO" property and introduces the
112	   "COORDINATES" (Section 4.1) property to replace it.  Implementations
113	   SHOULD NOT use the "GEO" property to represent spatial coordinates.
114	   Instead, they SHOULD specify the "COORDINATES" property in a
115	   "VLOCATION" component [RFC9073] (Section 7.2).  They MAY additionally
116	   specify a "GEO" property in a "VEVENT" or "VTODO" component, in which
117	   case its "DERIVED" parameter [RFC9073] (Section 5.3) MUST have value
118	   "TRUE".

120	   The remainder of this section documents the rationale for deprecating
121	   the "GEO" property:

123	   The "GEO" property definition dates back to 1998, a time at which
124	   multiple internet protocols and data formats incorporated spatial
125	   coordinates in slightly different formats, making interoperability
126	   difficult.  This got addressed in 2010 in [RFC5870], which introduced
127	   a Uniform Resource Identifier (URI) for geographic locations.  The
128	   'geo' URI scheme not only improves interoperability but also allows
129	   for richer information than the "GEO" property value, e.g. it
130	   supports specifying the location altitude and the spatial uncertainty
131	   of the coordinates.

133	   Alternatively to deprecating, this specification could have updated
134	   the "GEO" property to allow its property value type to be URI.  This
135	   turned out to not interoperate, as implementations tended to reject
136	   such iCalendar data as invalid.  This was regardless if the "GEO"
137	   property was specified in a "VEVENT" component, or if it was
138	   specified in iCalendar components that were unsupported by the
139	   implementation (e.g. an implementation that was unaware of the
140	   "VLOCATION" component still rejected the "GEO" property with value
141	   type URI in that component as invalid).  Introducing a new property
142	   turned out to better interoperate with such systems.

144	2.2.  COLOR Property

146	   This specification modifies the definition of the "COLOR" property,
147	   it allows its value to be a named color or a numeric color.  The
148	   following definitions replace the definitions of the "COLOR"
149	   property, originally specified in Section 5.9 of [RFC7986] from which
150	   the definitions for "Description", "Format Definition" and "Example"
151	   differ.

153	   Property Name:  COLOR

155	   Purpose:  This property specifies a color used for displaying the
156	      calendar, event, todo, or journal data.

158	   Value Type:  TEXT

160	   Property Parameters:  IANA and non-standard property parameters can
161	      be specified on this property.

163	   Conformance:  This property can be specified once in an iCalendar
164	      object or in "VEVENT", "VTODO", or "VJOURNAL" calendar components.

166	   Description:  This property specifies a color that clients MAY use
167	      when presenting the relevant data to a user.  Typically, this
168	      would appear as the "background" color of events or tasks.  The
169	      value is a color name taken from the set of names defined in
170	      Section 4.3 of [CSS3] or an RGB value in six-digit hexadecimal
171	      notation, as defined in Section 4.2.1 of [CSS3].  Values are case-
172	      insensitive.

174	   Format Definition:  This property is defined by the following
175	      notation:

177	      color       = "COLOR" colorparam ":" text CRLF
178	                    ; Value is CSS3 color name or CSS3 six-digit RGB hex value.

180	      colorparam     = *(";" other-param)

182	   Example:  The following are examples of this property:

184	      COLOR:turquoise
185	      COLOR:#40E0D0

187	      COLOR:#ffd755

189	3.  Updated Components

191	3.1.  VLOCATION component

193	   This document updates the definition of the "VLOCATION" component.
194	   It allows to specify the newly defined "COORDINATES" property
195	   (Section 4.1) at most once in a "VLOCATION" component.  It appends
196	   the following to the "Format Definition" of the "VLOCATION"
197	   component, defined in Section 7.2 of [RFC9073]:

199	   locprop /= *(
200	               ;
201	               ; The following is OPTIONAL
202	               ; but MUST NOT occur more than once.
203	               ;
204	               coord
205	               ;
206	               )

208	   The "coord" ABNF is defined in Section 4.1.

210	4.  New Properties

212	4.1.  COORDINATES Property

214	   Property Name:  COORDINATES

216	   Purpose:  To represent a geographic location using the protocol-
217	      independent, extensible "geo" URI scheme.

219	   Value Type:  URI -- no default

221	   Property Parameters:  IANA and non-standard parameters MAY be
222	      specified on this property.

224	   Conformance:  This property can be specified in a "VLOCATION"
225	      calendar component.

227	   Description:  This property represents spatial (geographic)
228	      coordinates.  In contrast to the the "GEO" property, this property
229	      allows to represent not only latitude and longitude but also
230	      altitude of a location.  In addition, it supports to indicate the
231	      uncertainty of the coordinates, is interoperable with other
232	      internet standards making use of spatial information, and is
233	      extensible, such as for use with other coordinate reference
234	      systems.  The property value MUST a URI in the "geo" URI scheme,
235	      as defined in [RFC5870] and updates.

237	   Format Definition:
238	      coord       = "COORDINATES" coordparam ":" uri CRLF

240	      coordparam  = *(
241	                     ;
242	                     ; The following is REQUIRED,
243	                     ; but MUST NOT occur more than once.
244	                     ;
245	                     (";" "VALUE" "=" "URI") /
246	                     ;
247	                     ; The following is OPTIONAL,
248	                     ; and MAY occur more than once.
249	                     ;
250	                     (";" other-param)
251	                     ;
252	                     )

254	   Example:  The following is an example of this property:

256	      COORDINATES;VALUE=URI:geo:48.198634,16.371648;crs=wgs84;u=40

258	4.2.  SHOW-WITHOUT-TIME Property

260	   Property Name:  SHOW-WITHOUT-TIME

262	   Purpose:  To indicate that the exact time span is not important when
263	      displaying this calendar object.

265	   Value Type:  BOOLEAN -- no default

267	   Property Parameters:  IANA and non-standard parameters can be
268	      specified on this property.

270	   Conformance:  This property can be specified in a "VEVENT" or "VTODO"
271	      calendar component.

273	   Description:  This indicates that the exact time span is not
274	      important to display when rendering this calendar object.  An
275	      example of this is an event that occurs over a full or almost full
276	      day, but in contrast to a DATE value is limited to a specific time
277	      zone or business hours.  While the time component is important for
278	      free-busy calculations and checking for scheduling clashes,
279	      calendars may choose to display it as an all-day event, or display
280	      the object separately to other objects to enhance the user's view
281	      of their schedule.

283	      This property only is for presentation purposes, it does not have
284	      any impact on the temporal span or value type of a calendar
285	      object.

287	      This property MAY be specified on VEVENT components where the
288	      DTSTART property is of type DATE-TIME, or in VTODO components
289	      where either the DTSTART or DUE property is specified and has type
290	      DATE-TIME.  In all other cases it MUST NOT be set.  If this
291	      property is set, its property value MUST be "TRUE", e.g. it MUST
292	      be omitted rather than having value "FALSE".

294	      Implementations that are unaware of the "SHOW-WITHOUT-TIME"
295	      property might inadvertently preserve this property when changing
296	      a calendar object's temporal type from DATE-TIME to DATE.
297	      Implementations SHOULD therefore ignore rather than reject the
298	      incorrectly specified SHOW-WITHOUT-TIME property.  They MUST NOT
299	      preserve the ill-specified property in the calendaring data.

301	   Format Definition:
302	      showwt      = "SHOW-WITHOUT-TIME" showwtparam ":" "TRUE" CRLF

304	      showwtparam = *(
305	                     ;
306	                     ; The following is REQUIRED,
307	                     ; but MUST NOT occur more than once.
308	                     ;
309	                     (";" "VALUE" "=" "BOOLEAN") /
310	                     ;
311	                     ; The following is OPTIONAL,
312	                     ; and MAY occur more than once.
313	                     ;
314	                     (";" other-param)
315	                     ;
316	                     )

318	   Example:
319	      SHOW-WITHOUT-TIME;VALUE=BOOLEAN:TRUE

321	5.  New Values

323	5.1.  OWNER Participation Role

325	   Value:  OWNER

327	   Purpose:  This participation role indicates that the calendar user is
328	      an owner of the calendar object.  This signifies they can make
329	      changes that affect all calendar users participating in this
330	      calendar object (for example, rescheduling the calendar object,
331	      adding and removing attendees and roles).  The presence of this
332	      role is only indicative; its semantics are subject to the
333	      calendaring exchange protocol being used.  See
334	      [I-D.ietf-jmap-calendars] for an example of making use of this
335	      role.

337	   Conformance:  This value can be used with the "ROLE" parameter.

339	   Example(s):
340	      ATTENDEE;ROLE=OWNER;RSVP=TRUE:mailto:jsmith@example.com

342	6.  Security Considerations

344	   This specification extends [RFC5545].  The same security
345	   considerations as outlined in Section 7 of [RFC5545] apply.

347	   The OWNER participation role (Section 5.1) is indicative only: its
348	   presence in an iCalendar object does not by itself grant any
349	   authorization.  Implementations MUST NOT grant a calendar user the
350	   ability to make changes to a calendar object based solely on the
351	   presence of this role; authorization is determined by the calendaring
352	   exchange protocol in use.  In the context of JMAP Calendars
353	   [I-D.ietf-jmap-calendars], this role is equivalent to the "owner"
354	   role of the Participant object.  Its semantics in the context of
355	   other calendaring exchange protocols, such as CalDAV [RFC4791], are
356	   not defined by this document.
