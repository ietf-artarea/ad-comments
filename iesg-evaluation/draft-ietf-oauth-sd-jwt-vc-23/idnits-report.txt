135	1.  Introduction

137	1.1.  Issuer-Holder-Verifier Model

139	   In the so-called Issuer-Holder-Verifier Model, Issuers issue
140	   Verifiable Digital Credentials to a Holder, who can then present the
141	   credentials to Verifiers.  Verifiable Digital Credentials are
142	   cryptographically secured statements about a Subject, typically the
143	   Holder.

145	   Figure 1 depicts the Issuer-Holder-Verifier model.

147	            +------------+
148	            |            |
149	            |   Issuer   |
150	            |            |
151	            +------------+
152	                  |
153	           Issues SD-JWT VC
154	                  |
155	                  v
156	            +------------+
157	            |            |
158	            |   Holder   |
159	            |            |
160	            +------------+
161	                  |
162	          Presents SD-JWT VC
163	                  |
164	                  v
165	            +-------------+
166	            |             |-+
167	            |  Verifiers  | |-+
168	            |             | | |
169	            +-------------+ | |
170	              +-------------+ |
171	                +-------------+

173	      Figure 1: Abstract Depiction of the Issuer-Holder-Verifier Model

175	   Verifiers can check the authenticity of the data in Verifiable
176	   Digital Credentials.  Verifiers can also optionally enforce Key
177	   Binding, which requires the Holder to prove they are the intended
178	   Holder of the Verifiable Digital Credential.  This proof is typically
179	   done by demonstrating possession of a cryptographic key referenced in
180	   the credential.  This process is further described in [RFC9901].

182	1.2.  SD-JWT as a Credential Format

184	   JSON Web Tokens (JWTs) [RFC7519] can in principle be used to express
185	   Verifiable Digital Credentials in a way that is easy to understand
186	   and process as it builds upon established web primitives.

188	   Selective Disclosure JWT (SD-JWT) [RFC9901] is a specification that
189	   introduces conventions to support selective disclosure for JWTs: For
190	   an SD-JWT document, a Holder can decide which claims to release
191	   (within bounds defined by the Issuer).

193	   SD-JWT builds on JWT/JWS.  It can also be used when there are no
194	   selectively disclosable claims.  However, SD-JWT itself does not
195	   define the claims that must be used within the payload or their
196	   semantics.

198	   This specification uses SD-JWT and the well-established JWT content
199	   rules and extensibility model as basis for representing Verifiable
200	   Digital Credentials with JSON payloads.  These Verifiable Digital
201	   Credentials are called SD-JWT VCs.  The use of selective disclosure
202	   in SD-JWT VCs is optional.

204	   An SD-JWT VC is verifiable through the Issuer's signature and, when
205	   Key Binding is used, through the Holder's proof of possession of the
206	   key referenced in the cnf claim.  What the credential means, that is,
207	   the semantics of its claims, is identified by its type, which is
208	   conveyed in the vct claim Section 2.2.2.1.  Type Metadata Section 5
209	   can be retrieved for a type and describes it to Consumers, including
210	   how the credential and its claims are displayed.  The aka_vcts claim
211	   Section 2.2.2.2 lists further types that the credential also has.

213	   SD-JWT VCs can contain claims that are registered in "JSON Web Token
214	   Claims" registry as defined in [RFC7519], as well as public and
215	   private claims.

225	1.4.  Terms and Definitions

227	   This specification uses the terms "Holder", "Issuer", "Verifier",
228	   "Disclosure", "Selectively Disclosable JWT (SD-JWT)", "Key Binding",
229	   "Key Binding JWT (KB-JWT)", "Selectively Disclosable JWT with Key
230	   Binding (SD-JWT+KB)" defined by [RFC9901].

232	   Consumer:  An application retrieving and processing documents and
233	      resources defined in this specification, in particular the Type
234	      Metadata specified in Section 5.  This typically includes Issuers,
235	      Verifiers, and Holders.
236	   Publisher:  An entity that publishes Type Metadata or other auxiliary
237	      documents referenced by an SD-JWT VC (for example via a vct URI),
238	      but that is not necessarily the Issuer of the SD-JWT VC.  A
239	      Publisher can be a standardization body, community, ecosystem
240	      authority, or any other party defining credential types or
241	      associated metadata.
242	   Verifiable Digital Credential:  An assertion with claims about a
243	      Subject that is cryptographically secured by an Issuer (usually by
244	      a digital signature).
245	   SD-JWT-based Verifiable Digital Credential (SD-JWT VC):  A Verifiable
246	      Digital Credential encoded using the format defined in [RFC9901].
247	      It may or may not contain selectively disclosable claims.  Note
248	      that the three-word term “Verifiable Digital Credential” is used
249	      to distinguish it from the W3C Verifiable Credentials Data Model
250	      and to better align with preferred terminology emerging elsewhere
251	      (see, for example, [NIST-BLOG.VDCE]).  However, the “D” is omitted
252	      in the short form “SD-JWT VC” in order to preserve the name that
253	      has been widely used to refer to this specification since its
254	      inception.
255	   Unsecured Payload of an SD-JWT VC:  A JSON object containing all
256	      selectively disclosable and non-selectively disclosable claims of
257	      the SD-JWT VC.  The Unsecured Payload acts as the input JSON
258	      object to issue an SD-JWT VC complying to this specification.

260	2.  Verifiable Digital Credentials based on SD-JWT

262	   This section defines encoding, validation and processing rules for
263	   SD-JWT VCs.

265	2.1.  Media Type

267	   Where a media type is used to identify an SD-JWT VC compliant with
268	   this specification, it MUST be application/dc+sd-jwt, where the base
269	   subtype name dc stands for "digital credential".

271	2.2.  Data Format

273	   SD-JWT VC uses the SD-JWT format defined in Section 4 of [RFC9901].
274	   Use of the JWS JSON Serialization per Section 8 of [RFC9901] for SD-
275	   JWT VC is not precluded but the specific details are beyond the scope
276	   of this specification.

278	   Note that in some cases, an SD-JWT VC MAY have no selectively
279	   disclosable claims, and therefore the encoded SD-JWT will not contain
280	   any Disclosures.

282	2.2.1.  JOSE Header

284	   This section defines JWT header parameters for the SD-JWT component
285	   of the SD-JWT VC.

287	   The Issuer MUST include the typ header parameter in the SD-JWT.  The
288	   typ value MUST use dc+sd-jwt.  This indicates that the payload of the
289	   SD-JWT contains plain JSON and follows the rules defined in this
290	   specification.  It further indicates that the SD-JWT is an SD-JWT
291	   component of an SD-JWT VC.

293	   Figure 2 is an example of a decoded SD-JWT header:

295	   {
296	     "alg": "ES256",
297	     "typ": "dc+sd-jwt"
298	   }

300	                     Figure 2: Decoded SD-JWT VC Header

302	2.2.2.  JWT Claims Set

304	   This section defines the claims that can be included in the payload
305	   of SD-JWT VCs.

307	2.2.2.1.  Verifiable Digital Credential Type - vct Claim

309	   This specification defines the new JWT claim vct (for verifiable
310	   credential type).  Its value MUST be a case-sensitive string serving
311	   as an identifier for the type of the SD-JWT VC.  The vct value MUST
312	   be a Collision-Resistant Name as defined in Section 2 of [RFC7515].

314	   A type is associated with rules defining which claims are permitted
315	   or required to appear in the Unsecured Payload of the SD-JWT VC and
316	   whether selective disclosure is permitted, necessary, or prohibited
317	   for those claims.

319	   This specification does not define any vct values; instead it is
320	   expected that ecosystems using SD-JWT VCs define such values
321	   including the semantics of the respective claims and associated rules
322	   (e.g., policies for issuing and validating credentials beyond what is
323	   defined in this specification).

325	   For example, a value of https://credentials.example.com/
326	   identity_credential can be associated with rules that define that at
327	   least the registered JWT claims given_name, family_name, birthdate,
328	   and address must appear in the Unsecured Payload.  Additionally, the
329	   registered JWT claims email and phone_number, and the private claims
330	   is_over_18, is_over_21, and is_over_65 may be used.  The type might
331	   also indicate that any of the aforementioned claims can be
332	   selectively disclosable.  The content in Figure 3 shows that vct
333	   value used to express the example type.

335	   {
336	     "vct": "https://credentials.example.com/identity_credential",
337	     "given_name": "Russ",
338	     "family_name": "Lasky",
339	     "birthdate": "1983-07-29",
340	     "address": {
341	       "street_address": "285 W Huntington Dr.",
342	       "locality": "Arcadia",
343	       "region": "CA",
344	       "postal_code": "91007"
345	     },
346	     "email": "sorryfolks@parksclosed.example",
347	     "exp": 1777707000,
348	     "cnf": {
349	       "jwk": {
350	         "kty": "EC", "crv": "P-256",
351	         "x": "TCAER19Zvu3OHF4j4W4vfSVoHIP1ILilDls7vCeGemc",
352	         "y": "ZxjiWWbZMQGHVWKVQ4hbSIirsVfuecCE6t4jT9F2HZQ"
353	       }
354	     }
355	   }

357	                Figure 3: Example Unsecured Payload with vct

359	   The vct value also effectively identifies the version of the
360	   credential type definition, as it ties a particular instance of a
361	   credential to a specific structure, set of semantics, and rules.
362	   When evolving a credential type without updating the version, changes
363	   to the structure or meaning of the associated claims need to be made
364	   in a way that preserves compatibility with existing implementations.

366	   If a change alters the meaning of existing content, adds new required
367	   claims, removes previously required elements, or otherwise introduces
368	   incompatibilities, it is generally advisable to treat that as a new
369	   version of the credential type and to convey it using a new vct
370	   value.  This allows different versions of a credential type to
371	   coexist and helps ensure that participants interpret credentials
372	   consistently.  For example, if such a need came about for the
373	   hypothetical type urn:example:eudi:pid:aendgard:1, a new version
374	   could be defined using a 'vct' of urn:example:eudi:pid:aendgard:2.

376	2.2.2.2.  Other Credential Types - aka_vcts Claim

378	   This specification defines the new JWT claim aka_vcts.  Its value
379	   MUST be a non-empty array of case-sensitive strings, each identifying
380	   an additional type of the SD-JWT VC.  Each value MUST be a Collision-
381	   Resistant Name as defined in Section 2 of [RFC7515], as required for
382	   vct values in Section 2.2.2.1.  The array MUST NOT contain the value
383	   of the vct claim of the SD-JWT VC.  The order of the values in the
384	   array is not significant and does not convey any information about
385	   the relationships between the types.

387	   An SD-JWT VC containing the aka_vcts claim is a Verifiable Digital
388	   Credential of the type identified by the vct claim and, additionally,
389	   of each of the types identified by the values in the aka_vcts claim.
390	   Holders and Verifiers can treat the SD-JWT VC as a credential of any
391	   of these types.  This is typically used when the type identified by
392	   the vct claim is derived from a more general type, which is then
393	   included in the aka_vcts claim.

395	   The aka_vcts claim is particularly useful in issuance and
396	   presentation protocols, where the receiving party (a Holder during
397	   issuance or a Verifier during presentation) matches the type of a
398	   received SD-JWT VC against the type it requested or expects.  For the
399	   purpose of type matching, a Holder or Verifier SHOULD treat an SD-JWT
400	   VC as being of a given type, if that type is the vct value or one of
401	   the values of the aka_vcts array.  While relationships between
402	   credential types can be expressed through the extends property in
403	   Type Metadata, Type Metadata is optional and may not be available, so
404	   issuance and presentation protocols cannot always rely on it for type
405	   matching.  For example, a Verifier requesting a credential of the
406	   hypothetical type urn:example:eudi:pid that receives an SD-JWT VC
407	   with a vct value of urn:example:eudi:pid:aendgard:1 can determine
408	   from an aka_vcts value of ["urn:example:eudi:pid"] that the received
409	   credential is also of the requested type.

411	   When the type in vct is derived from, extends, or is otherwise meant
412	   to be accepted as one or more general types, the Issuer SHOULD list
413	   those types in aka_vcts.

415	   The content in Figure 4 shows an excerpt of an Unsecured Payload
416	   using the aka_vcts claim to express this example.

418	   {
419	     "vct": "urn:example:eudi:pid:aendgard:1",
420	     "aka_vcts": [
421	       "urn:example:eudi:pid"
422	     ]
423	   }
424	         Figure 4: Example Unsecured Payload excerpt with aka_vcts

426	   Note that the aka_vcts claim is asserted by the Issuer and, like the
427	   vct claim, is only as trustworthy as the Issuer itself.

429	   The aka_vcts claim is independent of Type Metadata Section 5 and, in
430	   particular, orthogonal to the extends property: the claim can be used
431	   whether or not Type Metadata exists for any of the listed types, and
432	   the listed types are not required to be related to the type of the
433	   SD-JWT VC through the extends property.  The interaction between the
434	   aka_vcts claim and Type Metadata using the extends property is
435	   described in Section 5.4.

437	   Because the values of the aka_vcts claim are not used to retrieve
438	   Type Metadata, there is no aka_vcts#integrity counterpart to the
439	   vct#integrity claim; the integrity of Type Metadata reached via the
440	   extends property is covered by extends#integrity as described in
441	   Section 6.

443	2.2.2.3.  Registered JWT Claims

445	   SD-JWT VCs MAY use any claim registered in the "JSON Web Token
446	   Claims" registry as defined in [RFC7519].

448	   The following registered JWT claims, including any of their sub-
449	   claims, when used in the SD-JWT component of an SD-JWT VC, MUST NOT
450	   be included in Disclosures and therefore MUST NOT be selectively
451	   disclosed:

453	   *  iss: OPTIONAL.  As defined in Section 4.1.1 of [RFC7519] this
454	      claim explicitly indicates the Issuer of the Verifiable Digital
455	      Credential when it is not conveyed by other means (e.g., the
456	      subject of the end-entity certificate of an x5c header).
457	   *  nbf: OPTIONAL.  The time before which the Verifiable Digital
458	      Credential MUST NOT be accepted before validating.  See [RFC7519]
459	      for more information.
460	   *  exp: OPTIONAL.  The expiry time of the Verifiable Digital
461	      Credential after which the Verifiable Digital Credential is no
462	      longer valid.  See [RFC7519] for more information.
463	   *  cnf: OPTIONAL unless cryptographic Key Binding is to be supported,
464	      in which case it is REQUIRED.  Contains the confirmation method
465	      identifying the proof of possession key as defined in [RFC7800].
466	      It is RECOMMENDED that this contains a JWK as defined in
467	      Section 3.2 of [RFC7800].  For proof of cryptographic Key Binding,
468	      the KB-JWT in the presentation of the SD-JWT MUST be secured by
469	      the key identified in this claim.

471	   *  vct: REQUIRED.  The type of the Verifiable Digital Credential,
472	      e.g., https://credentials.example.com/identity_credential, as
473	      defined in Section 2.2.2.1.
474	   *  vct#integrity: OPTIONAL.  The hash of the Type Metadata document
475	      to provide integrity as defined in Section 6.
476	   *  aka_vcts: OPTIONAL.  An array of additional types of the
477	      Verifiable Digital Credential, as defined in Section 2.2.2.2.
478	   *  status: OPTIONAL.  The information on how to read the status of
479	      the Verifiable Digital Credential.  See
480	      [I-D.ietf-oauth-status-list] for more information.  When the
481	      status claim is present and using the status_list mechanism, the
482	      associated Status List Token MUST be in JWT format.

484	   The following registered JWT claims are used within the SD-JWT
485	   component of the SD-JWT VC and MAY be included in Disclosures, i.e.,
486	   can be selectively disclosed:

488	   *  sub: OPTIONAL.  The identifier of the Subject of the Verifiable
489	      Digital Credential.  The Issuer MAY use it to provide the Subject
490	      identifier known by the Issuer.  There is no requirement for a
491	      binding to exist between sub and cnf claims.
492	   *  iat: OPTIONAL.  The time of issuance of the Verifiable Digital
493	      Credential.  See [RFC7519] for more information.

495	   Note that Section 3 of [RFC7800] requires that a JWT containing a cnf
496	   claim also contain either the sub or iss claim.  This specification
497	   explicitly overrides that requirement, as there are valid and
498	   legitimate uses of key-bound SD-JWT VCs without either of those
499	   claims.

501	2.2.2.4.  Public and Private JWT claims

503	   Additionally, any public and private claims as defined in Sections
504	   4.2 and 4.3 of [RFC7519] MAY be used.

506	   Binary data in claims SHOULD be encoded as data URIs as defined in
507	   [RFC2397].  Exceptions can be made when data formats are used that
508	   already define a text encoding suitable for use in JSON or where an
509	   established text encoding is commonly used.  For example, images
510	   would make use of data URIs, whereas hash digests in base64 encoding
511	   do not need to be encoded as such.

513	   An example of a claim containing binary data encoded as a data URI is
514	   shown in Appendix A.1.

516	2.2.2.5.  SD-JWT VC without Selectively Disclosable Claims

518	   An SD-JWT VC MAY have no selectively disclosable claims.  In that
519	   case, the SD-JWT VC MUST NOT contain the _sd claim in the JWT body.
520	   It also MUST NOT have any Disclosures.

806	2.4.  Verification and Processing

808	   The recipient (Holder or Verifier) of an SD-JWT VC MUST process and
809	   verify an SD-JWT VC as described in Section 7 of [RFC9901].  The
810	   check in point 2.c of Section 7.1 of [RFC9901], which validates the
811	   Issuer and ensures that the signing key belongs to the Issuer, MUST
812	   be satisfied by determining and validating the public verification
813	   key used to verify the Issuer-signed JWT, employing a key discovery
814	   and validation mechanism (defined in Section 2.5) that is permitted
815	   for the Issuer according to policy.

817	   If Key Binding is required (refer to the security considerations in
818	   Section 9.5 of [RFC9901]), the Verifier MUST verify the KB-JWT
819	   according to Section 7.3 of [RFC9901].  To verify the KB-JWT, the cnf
820	   claim of the SD-JWT MUST be used.

822	   After the processed SD-JWT payload is available to the recipient, a
823	   Holder or Verifier MAY process Type Metadata as described in
824	   Section 5.7.  If Type Metadata is processed, the rules defined in
825	   Section 5.7 apply and can require the SD-JWT VC to be rejected.

827	   If there are no selectively disclosable claims, there is no need to
828	   process the _sd claim nor any Disclosures.

830	   If status is present in the verified payload of the SD-JWT, the
831	   status SHOULD be checked.  Verifier policy decides whether to reject
832	   or accept a presentation of a SD-JWT VC based on the status of the
833	   Verifiable Digital Credential.

835	   Additional validation rules MAY apply, but their use is out of the
836	   scope of this specification.

838	2.5.  Issuer Verification Key Discovery and Validation

840	   A key discovery and validation mechanism defines how a Verifier
841	   determines the appropriate key and associated procedure for verifying
842	   the signature of an Issuer-signed JWT.  This allows for flexibility
843	   in supporting different trust anchoring systems and key resolution
844	   methods without changing the core processing model.

846	   A recipient MUST determine and validate the public verification key
847	   for the Issuer-signed JWT using a supported key discovery and
848	   validation mechanism that is permitted for the given Issuer according
849	   to policy.  This specification defines the following two mechanisms:

851	   *  JWT VC Issuer Metadata: A mechanism to retrieve the Issuer's
852	      public key using web-based resolution.  When the value of the iss
853	      claim of the Issuer-signed JWT is an HTTPS URI, the recipient
854	      obtains the public key using the keys from JWT VC Issuer Metadata
855	      as defined in Section 4.

857	   *  Inline X.509 Certificates: A mechanism to retrieve the Issuer's
858	      public key using the X.509 certificate chain in the SD-JWT header.
859	      When the protected header of the Issuer-signed JWT contains the
860	      x5c parameter (Section 4.1.6 of [RFC7515]), the recipient uses the
861	      public key from the end-entity certificate of the certificates
862	      from that x5c header parameter and validates the X.509 certificate
863	      chain accordingly against a trust anchor permitted for the Issuer
864	      according to policy.  In this case, the Issuer of the Verifiable
865	      Digital Credential is the subject of the end-entity certificate.
866	      If the iss claim is also present, there is no requirement that its
867	      value directly correspond to a subject name in the end-entity
868	      certificate.

870	   To enable different trust anchoring systems or key resolution
871	   methods, separate specifications or ecosystem regulations may define
872	   additional key discovery and validation mechanisms that complement or
873	   override those defined above; however, the specifics of such
874	   mechanisms are out of scope for this specification.  See Section 7.3
875	   for related security considerations.

877	   If a recipient cannot validate that the public verification key
878	   corresponds to the Issuer of the Issuer-signed JWT using a permitted
879	   key discovery and validation mechanism, the SD-JWT VC MUST be
880	   rejected.

882	3.  Retrieving Documents and Resources via HTTP

884	   This specification defines several documents and resources that a
885	   Consumer retrieves via HTTP URLs: the JWT VC Issuer Metadata
886	   configuration and the JWK Set referenced by jwks_uri Section 4, Type
887	   Metadata documents referenced by vct claims and extends properties
888	   Section 5.3, and rendering resources such as logos, background
889	   images, and SVG templates Section 5.5.1.  The requirements in this
890	   section apply to every such retrieval.

892	   HTTP requests and responses used with this specification are governed
893	   by HTTP semantics [RFC9110] and HTTP caching [RFC9111].  A document
894	   or resource is retrieved by sending an HTTP GET request to its URL.
895	   A successful response carries a representation of the requested
896	   document or resource as its content; the expected media type of that
897	   representation is defined in the section defining the respective
898	   document or resource.  A Consumer MUST NOT use the content of an
899	   error response (a response with a 4xx or 5xx status code) in place of
900	   the requested document or resource.

902	   All URLs dereferenced according to this specification MUST use the
903	   HTTPS scheme.  As an exception, the rendering resource URIs defined
904	   in Section 5.5.1 MAY alternatively be data: URIs [RFC2397], which
905	   embed the resource and do not involve any retrieval.

907	   A server can respond to a request with an HTTP redirect (a 3xx status
908	   code, see Section 15.4 of [RFC9110]).  A Consumer that follows
909	   redirects MUST limit the number of redirects followed for a single
910	   retrieval, MUST NOT follow redirects to URLs not using the HTTPS
911	   scheme, and MUST apply the URL validation described in Section 7.1 to
912	   every URL it connects to, i.e., to the originally dereferenced URL as
913	   well as to every redirect target.

915	   Consumers MUST perform each retrieval in a time-bound and size-bound
916	   manner to prevent resource exhaustion and denial-of-service attacks,
917	   and MUST validate that the response content conforms to the format
918	   defined for the respective document or resource before processing it.

920	   Unless a document can be cached indefinitely based on integrity
921	   metadata as described in Section 5.3.4, the freshness and reuse of
922	   retrieved documents and resources is governed by the HTTP caching
923	   model [RFC9111].  Issuers and Publishers SHOULD include an explicit
924	   freshness lifetime (e.g., a Cache-Control: max-age response
925	   directive) in their responses.

927	4.  JWT VC Issuer Metadata

929	   This specification defines the JWT VC Issuer Metadata to retrieve the
930	   JWT VC Issuer Metadata configuration of the Issuer of the SD-JWT VC.
931	   The Issuer is identified by the iss claim in the JWT.  Use of the JWT
932	   VC Issuer Metadata is OPTIONAL.

934	   Issuers publishing JWT VC Issuer Metadata MUST make a JWT VC Issuer
935	   Metadata configuration available at the location formed by inserting
936	   the well-known string /.well-known/jwt-vc-issuer between the host
937	   component and the path component (if any) of the iss claim value in
938	   the JWT.  The iss MUST be a case-sensitive URL using the HTTPS scheme
939	   that contains scheme, host and, optionally, port number and path
940	   components as defined in [RFC3986], but no query or fragment
941	   components.  The path component, if present, MUST NOT contain any
942	   dot-segments (i.e., the discrete path segments "." and ".." described
943	   in Section 3.3 of [RFC3986]).

945	4.1.  JWT VC Issuer Metadata Request

947	   A JWT VC Issuer Metadata configuration MUST be queried using an HTTP
948	   GET request at the path defined in Section 4, following the rules
949	   defined in Section 3.

951	   Figure 12 is an example of an HTTP request for the JWT VC Issuer
952	   Metadata configuration when iss is set to https://example.com:

954	   GET /.well-known/jwt-vc-issuer HTTP/1.1
955	   Host: example.com

957	         Figure 12: Example HTTP Request for JWT VC Issuer Metadata

959	   If the iss value contains a path component, any terminating / MUST be
960	   removed before inserting /.well-known/ and the well-known URI suffix
961	   between the host component and the path component.

963	   Figure 13 is an example of an HTTP request for the JWT VC Issuer
964	   Metadata configuration when iss is set to https://example.com/
965	   tenant/1234:

967	   GET /.well-known/jwt-vc-issuer/tenant/1234 HTTP/1.1
968	   Host: example.com

970	         Figure 13: Example HTTP Request for JWT VC Issuer Metadata

972	4.2.  JWT VC Issuer Metadata Response

974	   A successful response carries a representation of the JWT VC Issuer
975	   Metadata configuration as its content, using the application/json
976	   media type.  The general requirements for HTTP retrieval defined in
977	   Section 3 apply.

979	   This specification defines the following JWT VC Issuer Metadata
980	   configuration parameters:

982	   *  issuer: REQUIRED.  The Issuer identifier, which MUST be identical
983	      to the iss value in the JWT.
984	   *  jwks_uri: OPTIONAL.  URL string referencing the Issuer's JSON Web
985	      Key (JWK) Set [RFC7517] document which contains the Issuer's
986	      public keys.  The value of this field MUST point to a valid JWK
987	      Set document.  The JWK Set document is retrieved as described in
988	      Section 3; its format and further processing are defined in
989	      [RFC7517].
990	   *  jwks: OPTIONAL.  Issuer's JSON Web Key Set [RFC7517] document
991	      value, which contains the Issuer's public keys.  The value of this
992	      field MUST be a JSON object containing a valid JWK Set.

994	   JWT VC Issuer Metadata MUST include either jwks_uri or jwks in their
995	   JWT VC Issuer Metadata, but not both.

998	   header parameter that can be used to look up the public key in the

1051	5.  SD-JWT VC Type Metadata

1053	   An SD-JWT VC type, i.e., the vct value, is associated with Type
1054	   Metadata defining, for example, information about the type and how
1055	   credentials are displayed.

1057	   This section defines Type Metadata that can be associated with a type
1058	   of an SD-JWT VC, as well as a method for retrieving the Type Metadata
1059	   and processing rules.  This Type Metadata is intended to be used,
1060	   among other things, for the following purposes:

1062	   *  Developers of Issuers and Verifiers can use the Type Metadata to
1063	      understand the semantics of the type and the associated rules.
1064	      While in some cases, Issuers are the parties that define types,
1065	      this is not always the case.  For example, a type can be defined
1066	      by a standardization body or a community.
1067	   *  Verifiers can use the Type Metadata to determine whether a
1068	      credential is valid according to the rules of the type.  For
1069	      example, a Verifier can check whether a credential contains all
1070	      required claims and whether the claims are selectively
1071	      disclosable.
1072	   *  Holders can use the metadata to display the credential in a way
1073	      that is consistent with the intent of the provider of the Type
1074	      Metadata.

1076	   Type Metadata can be retrieved as described in Section 5.3.
1077	   Ecosystems can define rules for a vct value that specify whether Type
1078	   Metadata is to be processed and which Type Metadata retrieval methods
1079	   Consumers are expected to support.

1081	5.1.  Type Metadata Example

1083	   This section only shows excerpts, the full examples can be found in
1084	   Appendix A.2.

1086	   The following in Figure 16 is an example of an SD-JWT VC payload,
1087	   containing a vct claim with the value
1088	   https://betelgeuse.example.com/education_credential/v42.

1090	   {
1091	     "vct": "https://betelgeuse.example.com/education_credential/v42",

1094	     ...
1095	   }

1097	            Figure 16: Example SD-JWT VC Payload with vct Claim

1099	   Type Metadata for the type
1100	   https://betelgeuse.example.com/education_credential/v42 can be
1101	   retrieved using various mechanisms as described in Section 5.3.  For
1102	   this example, the vct value is a URL as defined in Section 5.3.1 and
1103	   the Type Metadata document in Figure 17 is retrieved from it:

1105	   {
1106	     "vct":"https://betelgeuse.example.com/education_credential/v42",

1121	5.2.  Type Metadata Format

1123	   The Type Metadata document MUST be a JSON object.  The following
1124	   properties are defined:

1126	   *  vct: REQUIRED.  The verifiable digital credential type described
1127	      by this type metadata document.
1128	   *  name: OPTIONAL.  A human-readable name for the type, intended for
1129	      developers reading the JSON document.
1130	   *  description: OPTIONAL.  A human-readable description for the type,
1131	      intended for developers reading the JSON document.
1132	   *  extends: OPTIONAL.  A URI of another type that this type extends,
1133	      as described in Section 5.4.
1134	   *  display: An array of objects containing display information for
1135	      the type, as described in Section 5.5.  This property is OPTIONAL.
1136	   *  claims: An array of objects containing claim information for the
1137	      type, as described in Section 5.6.  This property is OPTIONAL.

1139	   Additionally, extends#integrity MAY be present as defined in
1140	   Section 6.

1142	   A Type Metadata document MAY contain additional top level or
1143	   subordinate properties.  Consumers MUST ignore properties that are
1144	   not understood.

1146	   An example of a Type Metadata document is shown in Appendix A.2.

1148	5.3.  Retrieving Type Metadata

1150	   A Consumer retrieving Type Metadata MUST ensure that the vct value in
1151	   the retrieved document is identical to the reference used to retrieve
1152	   it.  For the initial document, that reference is the SD-JWT VC's vct
1153	   claim value.  For a parent document, that reference is the immediate
1154	   child's extends property value.

1156	   If the claim vct#integrity is present in the SD-JWT VC, its value
1157	   MUST be an "integrity metadata" string as defined in Section 6.

1159	   The following sections define methods to retrieve Type Metadata.

1161	5.3.1.  From a URL in the vct Claim

1163	   A URI in the vct claim can be used to express a type.  If the type is
1164	   a URL using the HTTPS scheme, Type Metadata might be retrievable from
1165	   that URL, and it is at the consumer's discretion whether to attempt
1166	   to retrieve Type Metadata from the URL.

1168	   The Type Metadata is retrieved from that URL using an HTTP GET
1169	   request, following the rules defined in Section 3.  A successful
1170	   response carries a JSON object as defined in Section 5.2 as its
1171	   content, using the application/json media type.

1173	5.3.2.  From a Registry

1175	   A Consumer MAY use a registry to retrieve Type Metadata for a SD-JWT
1176	   VC type, e.g., if the type is not an HTTPS URL or if the Consumer
1177	   does not have access to the URL.  A Consumer needs to trust the
1178	   registry to provide correct Type Metadata for the type.

1180	   The registry MUST provide the Type Metadata in the same format as
1181	   described in Section 5.2.

1183	5.3.3.  Using a Defined Retrieval Method

1185	   Ecosystems MAY define additional methods for retrieving Type
1186	   Metadata.  For example, a standardization body or a community MAY
1187	   define a service which has to be used to retrieve Type Metadata based
1188	   on a URN in the vct claim.

1190	5.3.4.  From a Local Cache

1192	   A Consumer MAY cache Type Metadata for an SD-JWT VC type.  If a hash
1193	   for integrity protection is present for the Type Metadata as defined
1194	   in Section 6, the Consumer MAY assume that the Type Metadata is
1195	   static and cache it indefinitely, keyed by the integrity metadata
1196	   value.  Because the integrity metadata uniquely identifies the
1197	   content of the document, such a cache MAY be used regardless of any
1198	   caching directives (such as no-store) in the HTTP response.
1199	   Otherwise, the Consumer MUST determine how long the Type Metadata can
1200	   be cached and reused according to the HTTP caching model defined in
1201	   [RFC9111].  Publishers SHOULD therefore include an explicit freshness
1202	   lifetime (e.g., a Cache-Control: max-age response directive) in Type
1203	   Metadata responses, as described in Section 3.

1205	5.4.  Extending Type Metadata

1207	   An SD-JWT VC type can extend another type.  The extended type is
1208	   identified by the URI in the extends property.  Consumers MUST
1209	   retrieve and process Type Metadata for the extended type before
1210	   processing the Type Metadata for the extending type.

1212	   The extended type MAY itself extend another type.  This can be used
1213	   to create a chain or hierarchy of types.  The security considerations
1214	   described in Section 7.4 apply in order to avoid problems with
1215	   circular dependencies.

1217	   The extends property and the aka_vcts claim defined in
1218	   Section 2.2.2.2 are orthogonal mechanisms, and Type Metadata does not
1219	   add any requirements to the content of the aka_vcts claim.  However,
1220	   if Type Metadata exists both for the type in the vct claim and for a
1221	   type listed in the aka_vcts claim, the type of the SD-JWT VC SHOULD
1222	   extend the listed type, whether directly or transitively.  A Consumer
1223	   processing Type Metadata MAY use the types established via the
1224	   extends property in addition to those in the aka_vcts claim when
1225	   matching types.

1227	   Processing details when extending type metadata are described in
1228	   Section 5.5.2 and Section 5.6.5.

1230	5.5.  Display Metadata

1232	   The display property is an array containing display information for
1233	   the type.  The array contains an object for each locale that is
1234	   supported by the type.  The consuming application uses the object
1235	   containing the language tag it considers most appropriate for the
1236	   user.

1238	   The objects in the array have the following properties:

1240	   *  locale: A language tag as defined in Section 2 of [RFC5646].  This
1241	      property is REQUIRED.
1242	   *  name: A human-readable name for the type, intended for end users.
1243	      This property is REQUIRED.
1244	   *  description: A human-readable description for the type, intended
1245	      for end users.  This property is OPTIONAL.
1246	   *  dir: The base text direction of the human-readable string values
1247	      in this object, such as name and description, and in nested
1248	      objects, such as the alt_text of a logo in the rendering metadata,
1249	      as one of the strings ltr, rtl, or auto. ltr and rtl set the
1250	      paragraph direction for the Unicode Bidirectional Algorithm
1251	      [UAX9]; auto means that the direction is determined from the first
1252	      strong character of each value.  If absent, auto applies.  This
1253	      property is OPTIONAL.
1254	   *  rendering: An object containing rendering information for the
1255	      type, as described in Section 5.5.1.  This property is OPTIONAL.

1257	   The human-readable string values in a display object and its nested
1258	   objects are Unicode strings whose display direction follows from the
1259	   Unicode Bidirectional Algorithm [UAX9].  Where the default resolution
1260	   is not the intended one, Issuers can set the dir property or include
1261	   the Unicode directional formatting characters in the value.  The
1262	   language tag in locale can include a script subtag (Section 2.2.3 of
1263	   [RFC5646]).

1265	5.5.1.  Rendering Metadata

1267	   The rendering property is an object containing rendering information
1268	   for the type.  The object MUST contain a property for each rendering
1269	   method that is supported by the type.  The property name MUST be a
1270	   rendering method identifier and the property value MUST be an object
1271	   containing the properties defined for the rendering method.

1273	   The uri properties defined for the rendering methods below MUST be
1274	   either HTTPS URLs or data: URIs [RFC2397].  A resource referenced by
1275	   an HTTPS URL, including an SVG template, is retrieved as described in
1276	   Section 3; the requirements defined there, including those on
1277	   redirects, time and size bounds, and URL validation, apply to these
1278	   retrievals.  Logo and background images are expected to be served
1279	   with an appropriate image media type (e.g., image/png), and SVG
1280	   templates with the image/svg+xml media type.

1282	5.5.1.1.  Rendering Method "simple"

1284	   The simple rendering method is intended for use in applications that
1285	   do not support SVG rendering.  The object contains at least one of
1286	   the following properties:

1288	   *  logo: An object containing information about the logo to be
1289	      displayed for the type, as described in Section 5.5.1.1.1.  This
1290	      property is OPTIONAL.
1291	   *  background_image: An object containing information about the
1292	      background image to be displayed for the type, as described in
1293	      Section 5.5.1.1.2.  This property is OPTIONAL.
1294	   *  background_color: An RGB color value as defined in [W3C.CSS-COLOR]
1295	      for the background of the credential.  This property is OPTIONAL.
1296	   *  text_color: An RGB color value as defined in [W3C.CSS-COLOR] for
1297	      the text of the credential.  This property is OPTIONAL.

1299	5.5.1.1.1.  Logo Metadata

1301	   The logo property is an object containing information about the logo
1302	   to be displayed for the type.  The object contains the following
1303	   properties:

1305	   *  uri: A URI pointing to the logo image.  This property is REQUIRED.
1306	   *  uri#integrity: An "integrity metadata" string as described in
1307	      Section 6.  This property is OPTIONAL.
1308	   *  alt_text: A string containing alternative text for the logo image.
1309	      This property is OPTIONAL.

1311	5.5.1.1.2.  Background Image Metadata

1313	   The background_image property is an object containing information
1314	   about the background image to be displayed for the type.  The object
1315	   contains the following properties:

1317	   *  uri: A URI pointing to the background image.  This property is
1318	      REQUIRED.
1319	   *  uri#integrity: An "integrity metadata" string as described in
1320	      Section 6.  This property is OPTIONAL.

1322	5.5.1.2.  Rendering Method "svg_templates"

1324	   The svg_templates rendering method is intended for use in
1325	   applications that support SVG rendering. svg_templates MUST contain
1326	   an array of objects containing information about the SVG templates
1327	   available for the type.  Each object contains the following
1328	   properties:

1330	   *  uri: A URI pointing to the SVG template.  This property is
1331	      REQUIRED.
1332	   *  uri#integrity: An "integrity metadata" string as described in
1333	      Section 6.  This property is OPTIONAL.
1334	   *  properties: An object containing properties for the SVG template,
1335	      as described in Section 5.5.1.2.1.  This property is REQUIRED if
1336	      more than one SVG template is present, otherwise it is OPTIONAL.

1338	5.5.1.2.1.  SVG Template Properties

1340	   The properties property is an object containing properties for the
1341	   SVG template.  Consuming applications MUST use these properties to
1342	   find the best SVG template available for display to the user based on
1343	   the display properties (landscape/portrait) and user preferences
1344	   (color scheme, contrast).  The object contains at least one of the
1345	   following properties:

1347	   *  orientation: The orientation for which the SVG template is
1348	      optimized, with valid values being portrait and landscape.  This
1349	      property is OPTIONAL.
1350	   *  color_scheme: The color scheme for which the SVG template is
1351	      optimized, with valid values being light and dark.  This property
1352	      is OPTIONAL.
1353	   *  contrast: The contrast for which the SVG template is optimized,
1354	      with valid values being normal and high.  This property is
1355	      OPTIONAL.

1357	5.5.1.2.2.  SVG Rendering

1359	   A consuming application MUST preprocess the SVG template by replacing
1360	   placeholders in the SVG template with properly escaped values of the
1361	   claims in the credential.  The placeholders MUST be defined in the
1362	   SVG template using the syntax {{svg_id}}, where svg_id is an
1363	   identifier defined in the claim metadata as described in Section 5.6.

1365	   Placeholders MUST only be used in the text content of the SVG
1366	   template and MUST NOT be used in any other part of the SVG template,
1367	   e.g., in attributes or comments.

1369	   A consuming application MUST ensure that all special characters in
1370	   the claim values are properly escaped before inserting them into the
1371	   SVG template.  If invalid XML characters are present in the claim
1372	   values, the consuming application SHOULD reject and not render the
1373	   SVG template.  At least the following characters MUST be escaped:

1375	   *  & as &amp;
1376	   *  < as &lt;
1377	   *  > as &gt;
1378	   *  " as &quot;
1379	   *  ' as &apos;

1381	   If the svg_id is not present in the claim metadata, the consuming
1382	   application SHOULD reject and not render the SVG template.  If the
1383	   svg_id is present in the claim metadata, but the claim is not present
1384	   in the credential, the placeholder MUST be replaced with an empty
1385	   string or a string appropriate to indicate that the value is absent.
1386	   If the path of the claim metadata object selects more than one value,
1387	   the consuming application SHOULD reject and not render the SVG
1388	   template.

1390	   The example in Figure 18 shows a minimal SVG with one placeholder
1391	   using the svg_id value address_street_address which is defined in the
1392	   example in Appendix A.2.

1394	   <svg xmlns="http://www.w3.org/2000/svg" width="100" height="100">
1395	     <text x="10" y="20">Street address: {{address_street_address}}</text>
1396	   </svg>

1398	              Figure 18: Example SVG Template with Placeholder

1400	   See Section 7.10 for SVG template rendering security considerations.

1402	5.5.2.  Extending Display Metadata

1404	   When an SD-JWT VC type extends another type as described in
1405	   Section 5.4, the display metadata remains valid for the inheriting
1406	   type unless that type defines its own display property, in which case
1407	   the original display metadata is ignored.

1409	   Note that this does not affect the display properties in the claim
1410	   metadata.  Rules for these are defined in Section 5.6.5.

1412	5.6.  Claim Metadata

1414	   The claims property is an array of objects that provides per-claim
1415	   metadata.  Each object identifies which claim or set of claims in the
1416	   credential is being described (path), and can specify how that claim
1417	   is presented to end users (display), whether it is required to be
1418	   included by the Issuer (mandatory), whether it is selectively
1419	   disclosable (sd), and, for SVG rendering, which placeholder refers to
1420	   it (svg_id).

1422	   The array MAY contain an object for each claim that is supported by
1423	   the type.  Each object contains the following properties:

1425	   *  path: An array indicating the claim or claims that are being
1426	      addressed, as described below.  This property is REQUIRED.
1427	   *  display: An array containing display information for the claim or
1428	      claims that are being addressed, as described in Section 5.6.2.
1429	      This property is OPTIONAL.
1430	   *  mandatory: A boolean indicating that the claim must be present in
1431	      the issued credential.  This property is OPTIONAL.  If omitted,
1432	      the default value is false.  See Section 5.6.3 for details.
1433	   *  sd: A string indicating whether the claim is selectively
1434	      disclosable, as described in Section 5.6.4.  This property is
1435	      OPTIONAL.
1436	   *  svg_id: A string defining the ID of the claim for reference in the
1437	      SVG template, as described in Section 5.5.1.2.2.  The ID MUST be
1438	      unique within the type metadata.  It MUST consist of only
1439	      alphanumeric characters and underscores and MUST NOT start with a
1440	      digit.  It MUST NOT be used in a claim metadata object whose path
1441	      contains a null component, since such a path can select more than
1442	      one value.  This property is OPTIONAL.

1444	   When a Consumer processes Type Metadata for an SD-JWT VC, the claims
1445	   property MUST be an array of objects, and each of these objects MUST
1446	   conform to the definitions of the path, mandatory, and sd properties
1447	   in this section and its subsections; otherwise, claim metadata
1448	   processing fails.  Other properties, including display and svg_id, do
1449	   not cause claim metadata processing to fail.  Properties that are not
1450	   understood are ignored as defined in Section 5.2.

1452	   When a Holder or Verifier processes claim metadata for an SD-JWT VC,
1453	   it MUST validate the processed SD-JWT payload against the claim
1454	   metadata in the Type Metadata after applying any extensions as
1455	   described in Section 5.6.5.  Claim metadata validation fails if any
1456	   of the following applies:

1458	   *  Processing a path results in an error as defined in Section 5.6.1.
1459	   *  The Holder or Verifier can determine that a claim addressed by a
1460	      claim metadata object with mandatory set to true was not included
1461	      in the issued credential (see Section 5.6.3).
1462	   *  A claim selected by a claim metadata object's path is not
1463	      selectively disclosable as required by its sd value (see
1464	      Section 5.6.4).

1466	   Whether a mandatory claim was included can be determined by a Holder
1467	   that has all Disclosures by evaluating the path against the complete
1468	   Unsecured Payload.  A Verifier MUST NOT treat absence of a
1469	   selectively disclosable claim from a presentation as evidence that
1470	   the Issuer failed to include a mandatory claim.

1472	   When evaluating a path for this validation, the following applies:

1474	   *  A claim is selectively disclosable at a path if it is directly
1475	      represented as a Disclosure for an object property or array
1476	      element in the SD-JWT; it is not selectively disclosable solely
1477	      because one of its ancestors is.
1478	   *  Non-negative integer and null components of a path are evaluated
1479	      against the array as issued, counting array elements that are not
1480	      disclosed and are therefore absent from the processed SD-JWT
1481	      payload (see Section 5.6.1).
1482	   *  If a path selects an array element that is not disclosed, that
1483	      element was included in the issued credential and is selectively
1484	      disclosable; its contents are unknown, so any deeper path
1485	      components select no claims.

1487	   Performing this validation requires the Holder or Verifier to retain
1488	   sufficient information during SD-JWT processing, including the
1489	   positions of array elements that are not disclosed.  See Section 5.7
1490	   for the consequences of claim metadata processing and validation
1491	   failures.

1493	5.6.1.  Claim Path

1495	   The path property MUST be a non-empty array of strings, null values,
1496	   or non-negative integers.  It is used to select a particular claim in
1497	   the credential or a set of claims.  A string indicates that the
1498	   respective key is to be selected, a null value indicates that all
1499	   elements of the currently selected array(s) are to be selected, and a
1500	   non-negative integer indicates that the respective index in an array
1501	   is to be selected.

1503	5.6.1.1.  Example

1505	   Figure 19 shows a reduced example of a credential.

1507	   {
1508	     "vct": "https://betelgeuse.example.com/education_credential/v42",
1509	     "name": "Arthur Dent",
1510	     "address": {
1511	       "street_address": "42 Market Street",
1512	       "city": "Milliways",
1513	       "postal_code": "12345"
1514	     },
1515	     "degrees": [
1516	       {
1517	         "type": "Bachelor of Science",
1518	         "university": "University of Betelgeuse"
1519	       },
1520	       {
1521	         "type": "Master of Science",
1522	         "university": "University of Betelgeuse"
1523	       }
1524	     ],
1525	     "nationalities": ["British", "Betelgeusian"]
1526	   }

1528	                Figure 19: Example Credential for Claim Path

1530	   The following shows examples of path values and the respective
1531	   selected claims in the credential above:

1533	   *  ["name"]: The claim name with the value Arthur Dent is selected.
1534	   *  ["address"]: The claim address with its sub-claims as the value is
1535	      selected.
1536	   *  ["address", "street_address"]: The claim street_address with the
1537	      value 42 Market Street is selected.
1538	   *  ["degrees", null, "type"]: All type claims in the degrees array
1539	      are selected.

1541	   The example in Appendix A.2 shows how the path can be used to address
1542	   arrays and their elements.

1544	5.6.1.2.  Processing of path

1546	   In detail, the array components of path are processed from left to
1547	   right as follows:

1549	   1.  Select the root element of the credential, i.e., the top-level
1550	       JSON object.
1551	   2.  Process the path components from left to right:
1552	       1.  If the path component is a string, select the element in the
1553	           respective key in the currently selected element(s).  If any
1554	           of the currently selected element(s) is not an object, abort
1555	           processing and return an error.  If the key does not exist in
1556	           an element currently selected, remove that element from the
1557	           selection.
1558	       2.  If the path component is null, select all elements of the
1559	           currently selected array(s).  If any of the currently
1560	           selected element(s) is not an array, abort processing and
1561	           return an error.
1562	       3.  If the path component is a non-negative integer, select the
1563	           element at the respective index in the currently selected
1564	           array(s).  If any of the currently selected element(s) is not
1565	           an array, abort processing and return an error.  If the index
1566	           does not exist in a selected array, remove that array from
1567	           the selection.
1568	   3.  If the set of elements currently selected is empty, the result of
1569	       processing is the empty set.

1571	   The result of the processing is the set of elements to which the
1572	   respective claim metadata applies.

1574	   The path property MUST point to the respective claim as if the
1575	   payload was complete and conformant to the Type Metadata with all
1576	   selectively disclosable claims disclosed.  For a claim metadata
1577	   object with mandatory set to true (see Section 5.6.3), processing the
1578	   path against such a complete payload MUST NOT remove any element from
1579	   the selection in step 2 above; that is, every object traversed
1580	   contains the respective key and every array traversed contains the
1581	   respective index.  A missing intermediate key or index therefore
1582	   means that a mandatory claim is absent.  A null component applied to
1583	   an empty array selects nothing without violating this requirement.
1584	   That means that a consuming application which does not have access to
1585	   all disclosures may not be able to identify the claim which is being
1586	   addressed.

1588	   Note: This specification intentionally does not use JSON Pointer
1589	   [RFC6901] for selecting claims, as JSON Pointer requires string
1590	   parsing and does not support wildcard selection of array elements.
1591	   It does not use JSON Path [RFC9535] as that introduces a considerable
1592	   complexity and brings in many features which are not needed for the
1593	   use case of selecting claims in a credential.  There are also
1594	   security concerns with some implementations.

1596	5.6.2.  Claim Display Metadata

1598	   The display property is an array containing display information for
1599	   the claim.  The array contains an object for each locale that is
1600	   supported by the type.  The consuming application uses the object
1601	   containing the language tag it considers most appropriate for the
1602	   user.

1604	   The objects in the array have the following properties:

1606	   *  locale: A language tag as defined in Section 2 of [RFC5646].  This
1607	      property is REQUIRED.
1608	   *  label: A human-readable label for the claim, intended for end
1609	      users.  This property is REQUIRED.
1610	   *  description: A human-readable description for the claim, intended
1611	      for end users.  This property is OPTIONAL.
1612	   *  dir: The base text direction of the human-readable string values
1613	      in this object, such as label and description, and in nested
1614	      objects, with the same values and semantics as the dir property in
1615	      Section 5.5.  This property is OPTIONAL.

1617	   The considerations on the display direction of human-readable string
1618	   values in Section 5.5 apply to claim display objects as well.

1620	   See Figure 30 in Appendix A.2 for an example that includes claim
1621	   display metadata.

1623	5.6.3.  Claim Mandatory Metadata

1625	   The mandatory property is a boolean indicating that, if set to true,
1626	   the claim MUST be included in the credential by the Issuer.  If the
1627	   value is false or omitted, the claim is considered optional for the
1628	   Issuer to include.  A claim that is mandatory can nonetheless be
1629	   selectively disclosable, as described in Section 5.6.4.

1631	5.6.4.  Claim Selective Disclosure Metadata

1633	   The sd property is a string indicating whether the claim is
1634	   selectively disclosable.  The following values are defined:

1636	   *  always: The Issuer MUST make the claim selectively disclosable.
1637	   *  allowed: The Issuer MAY make the claim selectively disclosable.
1638	   *  never: The Issuer MUST NOT make the claim selectively disclosable.

1640	   If omitted, the default value is allowed.  It is RECOMMENDED to use
1641	   either always or never to avoid ambiguity.

1643	   See Figure 30 in Appendix A.2 for an example that includes claim
1644	   selective disclosure metadata.

1646	5.6.5.  Extending Claim Metadata

1648	   When an SD-JWT VC type extends another type as described in
1649	   Section 5.4, all claim metadata from the extended type MUST be
1650	   respected and are inherited by the child type unless it is overridden
1651	   by the child type as defined in the following.

1653	   If the child type defines claim metadata with the same path as in the
1654	   extended type, the child type's properties are combined with those of
1655	   the extended type, with the child type's properties taking
1656	   precedence.  Limitations to this rule are defined for sd and
1657	   mandatory in Section 5.6.5.1.

1659	   The contents of properties are never merged (e.g., if the base
1660	   display property contains two locale objects and the extending type
1661	   contains one, the resulting display property will contain only the
1662	   one object defined for the child type).

1664	   Note: The rule for overriding claim metadata is different from the
1665	   one for display metadata described in Section 5.5.2.  This ensures
1666	   that Consumers can rely on the claim metadata defined in the extended
1667	   type while still allowing display customization for the visual
1668	   representation of the credential.

1670	5.6.5.1.  Limitations for sd and mandatory

1672	   An extending type can specify an sd property for a claim that is
1673	   marked as allowed in the extended type (or where sd was omitted),
1674	   changing it to either always or never.  However, it MUST NOT change a
1675	   claim that is marked as always or never in the extended type to a
1676	   different value.

1678	   Similarly, an extending type can set the mandatory property of a
1679	   claim that is optional in the extended type to true, but it MUST NOT
1680	   change a claim that is mandatory in the extended type to false.

1746	5.7.  Processing Type Metadata

1748	   This specification does not require every Holder or Verifier to
1749	   process Type Metadata; whether Type Metadata is processed is
1750	   determined by the Holder's or Verifier's policy and, where
1751	   applicable, ecosystem rules.  A Holder or Verifier typically
1752	   processes Type Metadata after the processed SD-JWT payload is
1753	   available, as described in Section 2.4.

1755	   If Type Metadata is processed, it MUST be fully processed, including
1756	   any extended types (see Section 5.4), before its contents are used
1757	   for validation, display, rendering, or acceptance decisions.  If the
1758	   Type Metadata after applying any extensions contains claim metadata,
1759	   the Holder or Verifier MUST process and validate the claim metadata
1760	   as defined in Section 5.6.  If claim metadata processing or
1761	   validation fails, the SD-JWT VC MUST be rejected.

1763	   If Type Metadata processing is required by policy or ecosystem rules
1764	   and the Holder or Verifier cannot retrieve or process the applicable
1765	   Type Metadata, the SD-JWT VC MUST be rejected.

1767	6.  Integrity of Referenced Documents

1769	   This section defines how integrity can be asserted for documents
1770	   referenced by an SD-JWT VC and its Type Metadata.  For references
1771	   such as vct, extends, and uri, a corresponding #integrity value can
1772	   be used to identify the expected content of the retrieved document.
1773	   If such an integrity value is present, the Consumer verifies that the
1774	   retrieved document matches it before processing that document.

1776	   The vct claim in the SD-JWT VC as defined in Section 2.2.2.3 and
1777	   various URIs in the Type Metadata MAY be accompanied by a respective
1778	   item suffixed with #integrity, in particular:

1780	   *  extends as defined in Section 5.4, and
1781	   *  uri as used in three places in Section 5.5.1.

1783	   The value MUST be an "integrity metadata" string as defined in
1784	   Section 3 of [W3C.SRI].  This specification uses [W3C.SRI] only for
1785	   the syntax of that string and the identification of the hash
1786	   algorithms; the verification procedure is defined in the following.

1788	   If an integrity property is present for a claim or metadata property,
1789	   the Consumer of the referenced document MUST verify the integrity of
1790	   the retrieved document as follows: The Consumer computes the digest
1791	   of the octets of the retrieved document using the hash algorithm
1792	   identified in the integrity metadata and compares the result, after
1793	   base64 decoding, octet-for-octet with the digest value carried in the
1794	   integrity metadata.  If the integrity metadata contains multiple hash
1795	   expressions, the Consumer MUST use the hash expressions with the
1796	   strongest hash algorithm it supports; verification succeeds if the
1797	   computed digest matches the digest value of any of those hash
1798	   expressions.  If verification fails, or if the Consumer supports none
1799	   of the hash algorithms used in the integrity metadata, the retrieved
1800	   document MUST be rejected and MUST NOT be processed further.

1802	   Note that the verification procedure above is defined independently
1803	   of the response verification algorithm in [W3C.SRI].  That algorithm
1804	   is specified in terms of browser Fetch responses and makes integrity
1805	   validation contingent on the response being same-origin or CORS-
1806	   eligible, which does not apply to the retrieval mechanisms defined in
1807	   this specification.  Consequently, servers are not required to
1808	   support CORS for the referenced documents, and Consumers MUST NOT
1809	   make the verification result dependent on CORS response header
1810	   fields.

1812	7.  Security Considerations

1814	   The security considerations in the SD-JWT specification [RFC9901]
1815	   apply to this specification.  Additionally, the following security
1816	   considerations need to be taken into account when using SD-JWT VCs:

1818	7.1.  Server-Side Request Forgery

1820	   The URLs dereferenced according to this specification, e.g., for the
1821	   JWT VC Issuer Metadata configuration, the JWK Set referenced by
1822	   jwks_uri, Type Metadata, and rendering resources, are derived from
1823	   untrusted input such as the iss and vct claim values of a received
1824	   SD-JWT VC.  Similar to other metadata endpoints, these URLs MUST be
1825	   considered untrusted values and could be a vector for Server-Side
1826	   Request Forgery (SSRF) attacks.

1828	   Before making a request to any of these URLs, including every
1829	   redirect target as described in Section 3, the Consumer MUST validate
1830	   the URL to ensure that it is a valid HTTPS URL and that it does not
1831	   point to resources an issuer cannot access (e.g., resources internal
1832	   to the Consumer).  Such resources include, in particular, hosts with
1833	   addresses from the IANA Special-Purpose Address Registries [RFC6890]
1834	   that are not globally reachable (such as loopback, link-local, and
1835	   private-use address ranges) as well as hosts that are only reachable
1836	   from within the Consumer's network.  Validation requires ensuring
1837	   that the host part of the URL does not address an internal service
1838	   (by IP address or an internal host name) and that, if an external DNS
1839	   name is used, the resolved DNS name does not point to an internal IP
1840	   address.

1842	   The requirements in Section 3 to perform each retrieval in a time-
1843	   bound and size-bound manner and to validate the response content
1844	   before processing it also serve to limit the impact of SSRF and
1845	   denial-of-service attacks.

1847	   Additional considerations can be found in [OWASP_SSRF].

1849	7.2.  Serving Documents and Rendering Resources

1851	   The documents and resources defined in this specification are served
1852	   over HTTPS and therefore also remain reachable by web browsers and
1853	   other clients that do not implement this specification.  To limit the
1854	   risk of these documents and resources being misinterpreted or used as
1855	   active content in such contexts (see Section 4.13 of [RFC9205]),
1856	   Issuers and Publishers SHOULD include an X-Content-Type-Options:
1857	   nosniff response header field to prevent clients from interpreting a
1858	   response as a different media type than declared, and SHOULD include
1859	   a restrictive Content-Security-Policy response header field (e.g.,
1860	   default-src 'none') so that content such as SVG templates is not
1861	   granted access to active content capabilities when opened directly in
1862	   a browser.

1864	7.3.  Ecosystem-specific Public Key Verification Methods

1866	   When defining ecosystem-specific rules for resolution and
1867	   verification of the public key, as outlined in Section 2.5, it is
1868	   critical that those rules maintain the integrity of the relationship
1869	   between the iss value of the SD-JWT, if present, and the public keys
1870	   of the Issuer.

1872	   A Verifier MUST ensure that for any given iss value, an attacker
1873	   cannot influence the type of verification process used.  Otherwise,
1874	   an attacker could attempt to make the Verifier use a verification
1875	   process not intended by the Issuer, allowing the attacker to
1876	   potentially manipulate the verification result to their advantage.

1878	7.4.  Circular "extends" Dependencies of Types

1880	   A type MUST NOT extend another type that extends (either directly or
1881	   with steps in-between) the first type.  This would result in a
1882	   circular dependency that could lead to infinite recursion when
1883	   retrieving and processing the metadata.

1885	   Consumers MUST detect such circular dependencies and reject the
1886	   credential.

1888	7.5.  Robust Retrieval of Type Metadata

1890	   In Section 5.3, various methods for distributing and retrieving
1891	   metadata are described.  Methods relying on a network connection may
1892	   fail due to network issues or unavailability of a network connection
1893	   due to offline usage of credentials, temporary server outages, or
1894	   denial-of-service attacks on the metadata server.

1896	   Consumers SHOULD therefore implement a local cache as described in
1897	   Section 5.3.4 if possible.  Such a cache MAY be populated with
1898	   metadata before the credential is used.

1900	   These measures allow the Consumers to continue to function even if
1901	   the metadata server is temporarily unavailable and avoid privacy
1902	   issues as described in Section 8.4.

1904	7.6.  Risks Associated with Textual Information

1906	   Some claims in the SD-JWT VC and properties in the Type Metadata,
1907	   e.g., display, allow issuers and providers of metadata to specify
1908	   human-readable information.  These can contain arbitrary textual
1909	   information that may be displayed to end users and developers.  As
1910	   such, any consuming application MUST ensure that maliciously crafted
1911	   information cannot be used to compromise the security of the
1912	   application or the privacy of the user.  To this end, the following
1913	   considerations apply:

1915	   *  The consuming application MUST ensure that the text is properly
1916	      escaped before displaying it to the user or transferring it into
1917	      other contexts.  For example, if the data is displayed in an HTML
1918	      document, the text MUST be properly escaped to prevent Cross-Site
1919	      Scripting (XSS) attacks.
1920	   *  The consuming application MUST ensure that the display of the user
1921	      interface elements cannot be distorted by overly long text or
1922	      special characters.

1924	7.7.  Credential Type Extension and Issuer Authorization

1926	   When processing credentials, it is important to recognize that the
1927	   ability to extend or reference an existing credential type (e.g., a
1928	   well-known identifier such as urn:example:eudi:pid) does not confer
1929	   any implicit authorization to issue credentials of that type or its
1930	   extensions.  In particular:

1932	   *  *Issuer Authorization*: Verifiers and Holders MUST NOT assume that
1933	      any issuer who issues a credential extending a known type is
1934	      authorized to do so.  The mere presence of an extension or
1935	      reference to a recognized type (e.g., a national type
1936	      urn:example:de:pid extending a European PID type) does not
1937	      validate the issuer's authority.
1938	   *  *Rogue Issuers*: Attackers may issue credentials with types that
1939	      extend or mimic legitimate types (e.g., urn:example:attacker:pid
1940	      extending urn:example:eudi:pid).  Such credentials MUST NOT be
1941	      accepted solely based on their type hierarchy or extension
1942	      relationship.
1943	   *  *Processing Rules*: Implementations MUST verify the issuer's
1944	      authorization independently of the credential type or its
1945	      extensions.  This typically involves checking the issuer's
1946	      identity, trust status, and any relevant accreditation or registry
1947	      before accepting a credential.

1949	   Verifiers and Holders MUST implement explicit checks for issuer
1950	   authorization and MUST NOT rely on type extension as a proxy for
1951	   trust or legitimacy.  Credential acceptance decisions MUST be based
1952	   on both the credential type and the verified authority of the issuer.

1954	   The same considerations apply to the additional types asserted via
1955	   the aka_vcts claim defined in Section 2.2.2.2.  These types are
1956	   asserted by the Issuer and, for types without Type Metadata, cannot
1957	   be corroborated by an extends relationship.  Verifiers and Holders
1958	   therefore MUST NOT treat the presence of a type in the aka_vcts claim
1959	   as evidence that the Issuer is authorized to issue credentials of, or
1960	   derived from, that type.

1962	7.8.  Trust in Type Metadata

1964	   Type Metadata associated with an SD-JWT VC, e.g., rendering metadata,
1965	   is asserted by the Publisher of the Type Metadata and trust in this
1966	   metadata depends on the trust relationship between its Publisher and
1967	   the Consumer.  A Consumer MUST NOT assume that Type Metadata is
1968	   accurate or meaningful unless the Publisher is recognized as
1969	   authoritative for the type in question.

1971	   Ecosystems SHOULD define governance or accreditation mechanisms that
1972	   specify which Publishers are authorized to provide Type Metadata for
1973	   specific verifiable digital credential types and under what
1974	   conditions such metadata can be relied upon.

1976	   Consumers SHOULD treat with reduced trust any Type Metadata if the
1977	   Publisher is not accredited or otherwise trusted within the
1978	   applicable ecosystem.

1980	7.9.  Use of Data URIs for Claim Types

1982	   The use of data URIs allows embedding of data directly within
1983	   credential payloads.  Implementations SHOULD treat data URIs as
1984	   untrusted input at the processing and rendering layer and apply
1985	   appropriate validation and handling.  Failure to properly escape,
1986	   sanitize or constrain their use can lead to security issues such as
1987	   unintended code execution, resource exhaustion, or misuse of embedded
1988	   content.  Implementations SHOULD restrict the set of accepted media
1989	   types, enforce reasonable size and content limits, and avoid
1990	   dereferencing or interpreting data URIs in ways that could execute or
1991	   render active content, consistent with their overall security model.

1993	7.10.  SVG Rendering

1995	   When rendering an SVG template as described in Section 5.5.1.2.2, a
1996	   consuming application MUST ensure that malicious metadata providers
1997	   or issuers cannot inject executable code into the SVG template and
1998	   thereby compromise the security of the consuming application.  The
1999	   consuming application MUST NOT execute any code in the SVG template.
2000	   If code execution cannot be prevented reliably, the SVG display MUST
2001	   be sandboxed.

2003	   Furthermore, similar to retrieval of other metadata resources as
2004	   discussed in Section 8.4, consuming applications need to ensure that
2005	   references to external resources (images, etc.) from within the SVG
2006	   cannot be used to track users or the usage of credentials.

2008	8.  Privacy Considerations

2010	   The privacy considerations in the SD-JWT specification [RFC9901]
2011	   apply to this specification.  Additionally, the following privacy
2012	   considerations need to be taken into account when using SD-JWT VCs.

2014	8.1.  Unlinkability

2016	   The privacy considerations in Section 10.1 of [RFC9901] apply,
2017	   especially to the cnf claim.

2019	8.2.  Verifiable Digital Credential Type Identifier

2021	   Issuers and Holders have to be aware that while this specification
2022	   supports selective disclosure of claims of a given SD-JWT VC, the vct
2023	   claim is not selectively disclosable.  In certain situations this
2024	   could lead to unwanted leakage of additional context information.

2026	   In general, Issuers are advised to choose vct values following data
2027	   minimization principles.  For example, government Issuers issuing an
2028	   SD-JWT VC to their citizens to enable them to prove their age, might
2029	   consider using a vct value that does not allow third-parties to infer
2030	   additional personal information about the Holder or the Subject,
2031	   e.g., country of residency or citizenship.

2033	   Additionally, Holders have to be informed that, besides the actual
2034	   requested claims, the vct information is shared with the Verifier.

2036	   The same considerations apply to the aka_vcts claim, which is also
2037	   not selectively disclosable and reveals the additional types of the
2038	   credential.

2040	8.3.  Issuer Phone-Home

2042	   A malicious Issuer can choose the Issuer identifier of the SD-JWT VC
2043	   to enable tracking the usage behavior of the Holder if the Issuer
2044	   identifier is Holder-specific and if the resolution of the key
2045	   material to verify the Issuer-signed JWT requires the Verifier to
2046	   phone home to the Issuer.

2048	   For example, a malicious Issuer could generate a unique value for the
2049	   Issuer identifier per Holder, e.g., https://example.com/issuer/
2050	   holder-1234 and host the JWT VC Issuer Metadata.  The Verifier would
2051	   create an HTTP GET request to the Holder-specific well-known URI when
2052	   the SD-JWT VC is verified.  This would allow the malicious Issuer to
2053	   keep track where and how often the SD-JWT VC was used.

2055	   Verifiers are advised to establish trust in an SD-JWT VC by pinning
2056	   specific Issuer identifiers and should monitor suspicious behavior
2057	   such as frequent rotation of those identifiers.  If such behavior is
2058	   detected, Verifiers are advised to reject SD-JWT VCs issued by those
2059	   Issuers and not to retrieve associated metadata.  Holders are
2060	   similarly advised to exercise caution with SD-JWT VCs if they contain
2061	   unexpected or easily correlatable information in the Issuer
2062	   identifier.

2064	   Another related concern arises from the use of confirmation methods
2065	   in the cnf claim that involve retrieving key material from a remote
2066	   source, especially if that source is controlled by the issuer.  This
2067	   includes, but is not limited to, the use of the x5u parameter in JWKs
2068	   (Section 4.6 of [RFC7517]), the jku parameter (Section 3.5 of
2069	   [RFC7800]), and cases where a URL is used in the kid parameter
2070	   (Section 3.4 of [RFC7800]).  Future confirmation methods may also
2071	   introduce remote retrieval mechanisms.  Issuers are advised not to
2072	   issue SD-JWT VCs with such cnf methods, and Verifiers and Holders are
2073	   advised not to follow or resolve remote references for key material
2074	   in the cnf claim.  Only confirmation methods that do not require
2075	   remote retrieval of key material SHOULD be supported.

2077	8.4.  Privacy-Preserving Retrieval of Type Metadata

2079	   In Section 5.3, various methods for distributing and retrieving Type
2080	   Metadata are described.  For methods which rely on a network
2081	   connection to a URL (e.g., provided by an Issuer), the Issuer and
2082	   other third parties may be able to track the usage of a credential by
2083	   observing requests to the Type Metadata URL.  The same applies to the
2084	   retrieval of rendering resources such as logos, background images,
2085	   and SVG templates referenced from Type Metadata as described in
2086	   Section 5.5.1.

2088	   Consumers SHOULD prefer methods for retrieving Type Metadata and the
2089	   resources it references that do not leak information about the usage
2090	   of a credential to third parties.  The caching recommendations in
2091	   Section 7.5 apply and potentially identifying information about the
2092	   Holder or Consumer should not be included in any request to retrieve
2093	   such resources (e.g., in HTTP headers).

3057	       marked as sd: always, meaning each degree object will be
3058	       selectively disclosed as a whole.
3059	   3.  The field_of_study property of each degree object is marked as
3060	       sd: never, meaning that if the respective degree object is
3061	       disclosed, the field_of_study property will always be included
3062	       and cannot be hidden.
3063	   4.  The date_awarded property of each degree object is marked as sd:
3064	       always, meaning it can be selectively disclosed.
